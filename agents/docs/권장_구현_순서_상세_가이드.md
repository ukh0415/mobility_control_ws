# 휠 ↔ 트랙 모드 전환 권장 구현 순서 상세 가이드

## 1. 문서 목적

이 문서는 [`휠_트랙_모드_전환_시퀀스.md`](./휠_트랙_모드_전환_시퀀스.md)의 **13. 권장 구현 순서**를 실제 개발과 시험에서 차례로 수행할 수 있도록 세분화한 실행 가이드다.

각 단계는 다음 순서로 진행한다.

```text
단독 구현
  → 정적 검증과 컴파일
  → 저속·저출력 실기 시험
  → 실패 조건 시험
  → 결과 기록
  → 다음 단계 진행
```

안전과 직접 연결되는 단계 전환, 완료 판정 및 인터록은 PC나 ESP32 통신에 의존하지 않고 STM32 내부에서 수행한다.

## 2. 현재 구현 상태

현재 저장소를 기준으로 확인된 상태는 다음과 같다.

- 모터 3개의 수동 정회전·역회전이 가능하다.
- 모터1 엔코더 입력 채널이 구현되어 있다.
- 모터1 실기구동과 단일 STM32의 I2C 통신이 확인되었다.
- 모터2 엔코더, 캐리어 원점 센서, 모터3 클러치 a/b 센서는 추가 구성이 필요하다.
- 모터 제어는 아직 고정 PWM 명령 기반이다.
- STM32-ESP32 통신은 1바이트 명령과 3바이트 상태 응답을 사용한다.
- ESP32의 `ACTIVE_LEG_COUNT`는 단일 모듈 시험을 위해 `1`로 설정되어 있다.
- 현재 Git 기준 브랜치는 `main`이다.

주요 작업 파일은 다음과 같다.

```text
STM32: stm32/mobility/Core/Src/main.c
       stm32/mobility/Core/Inc/main.h
       stm32/mobility/mobility.ioc
ESP32: esp32/esp32_i2c_master/esp32_i2c_master.ino
Python: pc/robot_control_client_serial.py
프로토콜: protocol/protocol.md
```

## 3. 구현 시작 전 준비

### 3.1 기능 브랜치 생성

실제 코드를 수정하기 전에 `main`이 아닌 기능 브랜치를 만든다.

```powershell
git switch -c feature/sensor-feedback-control
```

단계별 변경이 커지면 다음처럼 브랜치를 나눌 수 있다.

```text
feature/sensor-inputs
feature/encoder-conversion
feature/motor1-speed-control
feature/motor2-position-control
feature/local-state-machine
feature/packet-protocol
```

### 3.2 하드웨어 사양 확정

2단계 이후의 환산과 폐루프 제어에 필요한 값을 먼저 조사하고 표로 기록한다.

| 구분 | 필요한 값 |
|---|---|
| 모터1 엔코더 | PPR 또는 CPR, 판독 체배, 엔코더 설치 축 |
| 모터1 기구 | 감속비, 휠 반지름 |
| 모터2 엔코더 | PPR 또는 CPR, 판독 체배, 감속비, 설치 축 |
| 유성기어 | 선기어 잇수, 링기어 잇수, 후단 감속비 |
| 캐리어 | 휠 기준 각도, 트랙 목표 각도, 허용 오차 |
| 모터3 센서 | 클러치 a/b 센서 종류, 입력 논리, 구동 방향 |
| 전체 모터 | 허용 RPM, 최대 PWM 또는 전류, 정지 판정 RPM |
| 안전 | 캐리어 정렬 및 클러치 전환 제한 시간 |

데이터시트 값과 실측값은 구분하여 기록한다.

```text
encoder_ppr_datasheet
encoder_cpr_measured
motor2_gear_ratio
wheel_radius_mm
carrier_angle_tolerance_tenths
clutch_timeout_ms
```

확정하지 못한 값은 추측을 사실처럼 사용하지 않고 `미확정`으로 표시한다.

### 3.3 시험 환경 준비

초기 시험은 다음 조건에서 수행한다.

- 다리 모듈 1개만 연결한다.
- 무부하이거나 바퀴를 지면에서 띄운 상태로 시험한다.
- 낮은 PWM과 낮은 목표 속도부터 시작한다.
- `k` 정지 명령과 별도의 모터 전원 차단 수단을 준비한다.
- 센서와 MCU의 전압 레벨을 확인한다.
- ESP32, STM32, 모터 드라이버와 모터 전원 사이에 공통 GND를 연결한다.
- 단일 기능 검증 중에는 나머지 모터 출력을 강제로 0으로 유지한다.

## 4. 1단계: 각 모터의 센서 입력 검증

이 단계에서는 PID 제어를 구현하지 않는다. 목적은 모터의 실제 운동 및 기구 위치와 센서 입력이 정확히 대응하는지 확인하는 것이다.

### 4.1 모터1 엔코더 검증

현재 모터1 엔코더 핀은 다음과 같다.

```text
A상: PA4 / EXTI4
B상: PA5 / GPIO 입력
```

시험 순서:

1. 모터를 손으로 정방향으로 돌린다.
2. `encoderCount`가 일정한 방향으로 증가하거나 감소하는지 확인한다.
3. 역방향으로 돌렸을 때 카운트 방향이 반대로 바뀌는지 확인한다.
4. 모터 정지 중 값이 흔들리거나 증가하지 않는지 확인한다.
5. 출력축을 정확히 1회전시켜 카운트 변화량을 기록한다.
6. 같은 시험을 최소 5회 반복해 측정값의 일관성을 확인한다.
7. 저속 모터 구동 중 카운트 누락과 비정상 점프가 없는지 확인한다.

현재 구현은 A상 상승 에지만 인터럽트로 판독하므로 데이터시트의 PPR 또는 CPR을 그대로 적용하면 안 된다. 현재 코드와 배선으로 얻는 출력축 1회전당 카운트를 직접 측정해야 한다.

완료 기준:

```text
정방향 회전에서 카운트 부호가 일정함
역방향 회전에서 반대 부호가 나타남
정지 상태에서 유의미한 카운트 변화가 없음
출력축 1회전 카운트의 반복 측정 오차가 허용 범위 이내임
```

### 4.2 모터2 엔코더와 원점 센서 추가

모터2는 캐리어 위치 제어와 트랙 속도 제어를 모두 수행하므로 모터1과 독립된 엔코더 채널이 필요하다.

1. STM32의 남는 GPIO, EXTI와 타이머 채널을 조사한다.
2. 가능하면 타이머 Encoder Mode를 사용한다.
3. 타이머 Encoder Mode를 사용할 수 없다면 A상 인터럽트와 B상 방향 판독을 구성한다.
4. 모터별 엔코더 카운트를 분리한다.

예시:

```c
volatile int32_t wheel_encoder_count;
volatile int32_t sun_encoder_count;
```

5. 모터2를 손으로 정·역회전시켜 카운트 부호를 확인한다.
6. 모터축 또는 출력축 1회전당 카운트를 반복 측정한다.
7. 캐리어 원점 센서가 눌렸을 때 입력이 정확히 바뀌는지 확인한다.
8. 센서 입력에 기계적 바운스가 있다면 디바운싱을 적용한다.

원점 센서는 예를 들어 입력이 10ms 이상 같은 상태를 유지할 때 활성으로 판정할 수 있다. 실제 디바운스 시간은 센서 측정 결과를 근거로 정한다.

### 4.3 모터3 클러치 a/b 센서 검증

권장 입력은 다음과 같다.

```text
CLUTCH_A_LIMIT
CLUTCH_B_LIMIT
```

입력 조합의 의미를 명확하게 정의한다.

| a 센서 | b 센서 | 판정 |
|---:|---:|---|
| 1 | 0 | 클러치 a 체결 |
| 0 | 1 | 클러치 b 체결 |
| 0 | 0 | 전환 중 또는 미체결 |
| 1 | 1 | 센서 또는 배선 오류 |

센서가 active-low이면 표의 논리값을 소프트웨어의 정규화된 활성 상태로 해석한다.

시험 순서:

1. 클러치를 a 위치에 놓고 a 센서만 활성인지 확인한다.
2. 중간 위치에서 두 센서가 비활성인지 확인한다.
3. 클러치를 b 위치에 놓고 b 센서만 활성인지 확인한다.
4. 케이블 단선 또는 분리 시 안전한 상태로 판정되는지 확인한다.
5. 부팅 직후 현재 위치를 올바르게 판별하는지 확인한다.
6. 두 센서 동시 활성 상태를 오류로 판정하는지 확인한다.

이 단계에서는 센서에 따른 자동 전환 제어를 구현하지 않고 입력 검증만 수행한다.

### 4.4 1단계 산출물과 완료 조건

- 확정된 센서 핀 배치표
- 센서별 active-high 또는 active-low 정의
- 엔코더 정방향 부호 정의
- 엔코더별 1회전당 실측 카운트
- 원점 센서와 클러치 a/b 센서 시험 결과
- 센서 단선과 센서 모순 상태의 판정 규칙

모든 센서 입력을 신뢰할 수 있다는 근거가 확보된 후 2단계로 진행한다.

## 5. 2단계: 엔코더 카운트를 실제 각도와 RPM으로 환산

이 단계의 목적은 원시 엔코더 카운트를 물리 단위로 변환하는 것이다. 아직 폐루프 모터 제어는 수행하지 않는다.

### 5.1 물리 상수 정의

매직 넘버를 사용하지 않고 단위가 드러나는 이름으로 상수를 정의한다.

```c
#define WHEEL_ENCODER_CPR            ...
#define WHEEL_GEAR_RATIO_NUM         ...
#define WHEEL_GEAR_RATIO_DEN         ...
#define SUN_ENCODER_CPR              ...
#define SUN_GEAR_RATIO_NUM           ...
#define SUN_GEAR_RATIO_DEN           ...
#define SPEED_SAMPLE_PERIOD_MS       20U
```

감속비가 정수가 아닐 가능성을 고려해 분자와 분모로 관리할 수 있다.

### 5.2 각도 계산

엔코더가 모터축에 있으면 다음 식을 사용한다.

```text
출력축 1회전 카운트 = 엔코더 CPR × 감속비
```

프로토콜의 각도 단위는 0.1도이므로 다음과 같이 환산한다.

```text
각도[0.1도] = count × 3600 / 출력축 1회전 카운트
```

중간 곱셈의 오버플로를 피하기 위해 64비트 정수를 사용한다.

```c
int32_t counts_to_angle_tenths(int32_t count)
{
    return (int32_t)(((int64_t)count * 3600) /
                     COUNTS_PER_OUTPUT_REV);
}
```

### 5.3 RPM 계산

고정된 샘플 주기마다 카운트 차이를 계산한다.

```text
delta_count = current_count - previous_count
RPM = delta_count × 60000
      / (counts_per_rev × sample_period_ms)
```

프로토콜에 맞춰 0.1 RPM 단위로 저장한다.

```c
typedef struct {
    int32_t count;
    int32_t previous_count;
    int32_t delta_count;
    int16_t rpm_tenths;
} EncoderFeedback;
```

RPM 노이즈가 크면 이동평균 또는 저역통과 필터를 적용한다. 필터가 너무 강하면 정지 판정이 늦어질 수 있으므로 실제 정지 응답을 함께 측정한다.

### 5.4 유성기어 환산

모터2는 클러치 상태에 따라 출력 관계가 달라진다.

```text
클러치 a: 선기어 입력 → 캐리어 각도
클러치 b: 선기어 입력 → 링기어 및 트랙 속도
```

따라서 다음과 같이 목적별 함수를 분리한다.

```c
sun_count_to_carrier_angle_tenths();
sun_rpm_to_track_rpm_tenths();
```

선기어와 링기어 잇수, 고정되는 요소와 후단 감속비가 확정된 뒤 유성기어 관계식을 적용한다. 값이 확정되지 않은 경우 모터2 환산 결과를 `미확정`으로 기록하고 제어에 사용하지 않는다.

### 5.5 2단계 검증과 완료 조건

- 출력축을 90도, 180도, 360도 움직여 계산 각도와 비교한다.
- 알려진 일정 RPM으로 구동해 타코미터 또는 영상 측정 결과와 비교한다.
- 정방향과 역방향의 부호를 확인한다.
- 장시간 회전에 따른 카운터 범위와 오버플로를 검토한다.
- 정지 상태에서 계산되는 RPM 노이즈를 측정한다.
- 측정 오차가 사전에 정한 허용 범위 안에 들어오는지 확인한다.

## 6. 3단계: 모터1 단독 속도 제어

모터1만 제어하고 모터2와 모터3 출력은 강제로 0으로 유지한다.

### 6.1 PID보다 먼저 구현할 안전 제한

다음 항목을 속도 제어기보다 먼저 구현한다.

- 목표 RPM 범위 제한
- 최대 PWM 또는 최대 전류 제한
- PWM 상승·하강률 제한
- 통신 두절 시 정지
- 엔코더 이상 시 정지
- 정지 명령 최우선 처리

예시 상수:

```c
#define WHEEL_MAX_RPM_TENTHS       ...
#define WHEEL_MAX_PWM_PERMILLE     ...
#define WHEEL_PWM_SLEW_PER_TICK    ...
#define WHEEL_STOP_RPM_TENTHS      ...
#define WHEEL_STOP_CONFIRM_MS      ...
#define COMMAND_TIMEOUT_MS         ...
```

### 6.2 고정 주기 제어 루프

제어 주기가 `while (1)`의 실행 속도에 따라 변하지 않도록 10ms 또는 20ms와 같은 고정 주기로 수행한다.

```text
엔코더 읽기
  → 측정 RPM 갱신
  → 목표와 측정값의 오차 계산
  → PID 출력 계산
  → 출력 범위 제한
  → 가속·감속 제한
  → 방향과 PWM 적용
```

### 6.3 PID 조정 순서

1. 처음에는 `Ki = 0`, `Kd = 0`으로 두고 P 제어만 시험한다.
2. 낮은 목표 RPM을 설정한다.
3. 진동 없이 목표를 따라갈 수 있을 때까지 `Kp`를 조금씩 높인다.
4. 정상상태 오차를 줄이기 위해 작은 `Ki`를 추가한다.
5. 적분기 포화 방지를 적용한다.
6. 측정 노이즈와 응답 특성상 꼭 필요한 경우에만 `Kd`를 검토한다.

시험은 다음 순서로 확대한다.

```text
저속 정방향
  → 저속 역방향
  → 중간 속도 정방향
  → 중간 속도 역방향
  → 목표 속도 계단 입력
  → 감속 및 정지
```

### 6.4 정지 판정

PWM을 0으로 설정한 사실만으로 정지를 판정하지 않는다.

```text
abs(measured_rpm) <= stop_threshold
그리고 위 조건이 stop_confirm_ms 이상 유지됨
```

이 판정은 이후 `모터1 정지 확인 후 모터2 허용` 인터록에 사용한다.

### 6.5 3단계 완료 조건

- 정방향과 역방향에서 목표 RPM을 안정적으로 추종한다.
- 정지 명령 후 제한 시간 내 정지한다.
- 엔코더 입력 이상 시 모터 출력을 유지하지 않고 오류 정지한다.
- 모터2와 모터3 출력이 항상 0으로 유지된다.
- 목표값, 측정값, PWM, 정착시간과 오버슈트를 기록한다.

## 7. 4단계: 모터2 단독 캐리어 위치 제어

이 단계에서는 클러치 a가 체결된 상태에서만 모터2 위치 제어를 허용한다.

### 7.1 부팅 시 원점 복귀

증분형 엔코더는 전원을 다시 인가하면 절대 위치를 알 수 없으므로 다음 절차가 필요하다.

```text
모든 모터 정지
  → 클러치 a 확인
  → 모터2를 낮은 PWM으로 원점 방향 구동
  → 원점 센서 확인
  → 모터2 정지
  → 엔코더 카운트 0 설정
  → 원점 복귀 완료
```

원점 센서가 제한 시간 안에 입력되지 않으면 모든 모터를 정지하고 오류 상태로 이동한다.

### 7.2 위치 제어

```text
목표 각도 - 현재 각도
          ↓
        위치 제어
          ↓
    방향 + 제한된 PWM
```

처음에는 P 제어로 시작한다. 목표 부근에서 PWM이 감소하도록 하고, 정지 마찰을 이기기 위한 최소 구동 PWM을 실측해 적용한다.

완료 조건은 위치 오차와 속도를 함께 사용한다.

```text
abs(position_error) <= angle_tolerance
AND abs(measured_rpm) <= stop_rpm_threshold
AND 위 상태가 settle_time_ms 이상 유지됨
```

각도 오차만 만족했다고 완료 처리하면 관성으로 목표 위치를 지나갈 수 있다.

### 7.3 시험 순서

```text
원점 → 작은 양의 각도
  → 작은 각도 → 원점
  → 원점 → 중간 각도
  → 중간 각도 → 원점
  → 트랙 목표 각도 → 원점
```

기계적 끝단에 가까운 목표부터 시험하지 않는다.

### 7.4 4단계 완료 조건

- 부팅 후 원점 복귀가 반복적으로 성공한다.
- 같은 목표각에 대한 반복 위치 오차가 허용 범위 이내이다.
- 센서 이상과 정렬 제한 시간 초과 시 모터2가 정지한다.
- 클러치 a가 아니면 위치 제어 시작을 거부한다.
- 모터2 동작 중 모터1과 모터3이 항상 정지한다.

## 8. 5단계: 모터2 트랙 속도 제어

클러치 b가 체결된 상태에서 모터2를 트랙 구동용 속도 제어기로 사용한다.

### 8.1 모터2 제어 모드 분리

```c
typedef enum {
    MOTOR2_IDLE,
    MOTOR2_POSITION_CONTROL,
    MOTOR2_SPEED_CONTROL
} Motor2ControlMode;
```

다음 조건을 강제한다.

```text
클러치 a → 캐리어 위치 제어만 허용
클러치 b → 트랙 속도 제어만 허용
전환 중 또는 센서 모순 → 모터2 구동 금지
```

### 8.2 속도 환산과 PID

제어 대상은 모터축 RPM이 아니라 최종 트랙 출력 RPM이다. 유성기어 잇수 관계와 후단 감속비를 모두 포함한다.

모터1 속도 제어 구조를 재사용할 수 있지만 모터1과 모터2의 PID 계수와 출력 제한값은 별도로 둔다.

### 8.3 시험 순서

1. 클러치 b의 실제 체결을 확인한다.
2. 낮은 목표 RPM으로 시작한다.
3. 정방향과 역방향을 각각 확인한다.
4. 가속·감속 제한이 동작하는지 확인한다.
5. 정지 명령 후 실제 정지시간을 측정한다.
6. 운전 중 클러치 b 센서가 사라지는 고장 조건에서 즉시 정지하는지 확인한다.

### 8.4 5단계 완료 조건

- 클러치 b에서만 트랙 구동이 가능하다.
- 목표 트랙 RPM을 허용 오차 내에서 추종한다.
- 정지 판정이 안정적으로 동작한다.
- 클러치 센서 모순 또는 b 센서 소실 시 출력을 차단한다.
- 모터2 트랙 구동 중 모터1과 모터3이 항상 정지한다.

## 9. 6단계: 모터3 클러치 a/b 전환과 시간 초과 처리

클러치 전환은 기구 충돌 위험이 크므로 매우 낮은 PWM과 무부하 조건에서 시작한다.

### 9.1 클러치 상태 정의

```c
typedef enum {
    CLUTCH_UNKNOWN,
    CLUTCH_A,
    CLUTCH_B,
    CLUTCH_SHIFTING_TO_A,
    CLUTCH_SHIFTING_TO_B,
    CLUTCH_FAULT
} ClutchState;
```

### 9.2 a에서 b로 전환

```text
모터1 정지 확인
  → 모터2 정지 확인
  → 모터3 정방향 저속 구동
  → 클러치 b 센서 확인
  → 모터3 즉시 정지
  → CLUTCH_B 확정
```

b에서 a로 전환할 때는 반대 방향으로 동일한 안전 조건을 적용한다.

### 9.3 제한 시간과 오류 처리

전환 시작 시각을 저장한다.

```c
clutch_shift_start_ms = HAL_GetTick();
```

다음 조건이면 시간 초과이다.

```text
HAL_GetTick() - clutch_shift_start_ms > clutch_timeout_ms
```

시간 초과 또는 센서 오류 발생 시 다음을 수행한다.

```text
모터3 정지
  → 모터1 정지
  → 모터2 정지
  → 오류 플래그 설정
  → FAULT 진입
```

### 9.4 추가 오류 조건

- a와 b 센서가 동시에 활성됨
- 전환 출발 위치와 목표 위치가 모순됨
- 전환 중 센서 입력이 비정상적으로 반복 변화함
- 목표 센서가 입력됐는데 모터3 출력이 계속 유지됨
- 모터1 또는 모터2가 움직이는 중 클러치 전환이 요청됨

### 9.5 6단계 완료 조건

- a→b와 b→a 전환이 반복적으로 성공한다.
- 목표 센서 입력 시 모터3이 즉시 정지한다.
- 목표 센서를 입력하지 않는 시험에서 제한 시간 후 정지한다.
- 모터1 또는 모터2 구동 중 전환 요청을 거부하거나 FAULT 처리한다.
- 모터3 동작 중 모터1과 모터2 출력이 항상 0이다.

## 10. 7단계: STM32 로컬 상태 머신과 인터록

앞 단계에서 검증한 개별 제어 기능을 안전한 전체 시퀀스로 통합한다.

```c
typedef enum {
    STATE_INITIALIZING,
    STATE_WHEEL_DRIVE,
    STATE_PREPARE_TRACK_MODE,
    STATE_SHIFT_CLUTCH_TO_B,
    STATE_TRACK_DRIVE,
    STATE_PREPARE_WHEEL_MODE,
    STATE_SHIFT_CLUTCH_TO_A,
    STATE_ALIGN_CARRIER_FOR_WHEEL,
    STATE_FAULT
} RobotState;
```

### 10.1 상태별 동작

| 상태 | 진입 동작 | 완료 조건 |
|---|---|---|
| `INITIALIZING` | 전체 정지, 원점과 클러치 위치 확인 | 센서 정상 및 원점 복귀 완료 |
| `WHEEL_DRIVE` | 모터2·3 정지, 모터1 속도 제어 | 트랙 모드 전환 요청 |
| `PREPARE_TRACK_MODE` | 모터1 정지 후 모터2 위치 제어 | 모터1 정지 및 트랙 목표각 도달 |
| `SHIFT_CLUTCH_TO_B` | 모터1·2 정지, 모터3 구동 | 클러치 b 센서 입력 |
| `TRACK_DRIVE` | 모터1·3 정지, 모터2 속도 제어 | 휠 모드 전환 요청 |
| `PREPARE_WHEEL_MODE` | 모터2 감속 및 정지 | 모터2 정지 확인 |
| `SHIFT_CLUTCH_TO_A` | 모터1·2 정지, 모터3 구동 | 클러치 a 센서 입력 |
| `ALIGN_CARRIER_FOR_WHEEL` | 모터2 위치 제어 | 휠 기준각 도달 및 정지 |
| `FAULT` | 모든 모터 즉시 정지 | 오류 해제 조건 확인 후 재초기화 |

### 10.2 상태 처리 구조

상태 진입 시 한 번만 수행할 처리와 매 제어 주기마다 수행할 처리를 분리한다.

```c
State_Enter(new_state);
State_Update();
State_Exit(old_state);
```

각 상태에는 다음 정보가 있어야 한다.

- 진입 시 모터 명령
- 허용되는 외부 명령
- 다음 상태 전환 조건
- 최대 허용 시간
- 센서 오류 조건
- 오류 발생 시 설정할 플래그

### 10.3 필수 인터록

- 모터1 정지 확인 전 캐리어 정렬을 시작하지 않는다.
- 모터2 정지 확인 전 모터3을 동작하지 않는다.
- 모터3 동작 중 모터1과 모터2를 정지한다.
- 클러치 b 체결 전 트랙 주행을 금지한다.
- 클러치 a 체결 전 캐리어 원위치 정렬과 휠 주행을 금지한다.
- 통신 두절, 센서 오류, 제한 시간 초과와 유효하지 않은 상태 전이 시 모든 모터를 정지한다.

`FAULT` 진입 시 상태 변수만 변경하지 말고 모든 PWM과 방향 출력을 실제 안전 상태로 만든다.

`CLEAR_FAULT`는 무조건 허용하지 않는다. 센서 모순이 해소되고 모든 모터가 정지했으며 초기화 절차를 다시 수행할 수 있을 때만 받아들인다.

## 11. 8단계: STM32-ESP32 I2C 명령 및 상태 패킷 확장

이 단계는 공용 프로토콜 변경이므로 코드를 수정하기 전에 `protocol/protocol.md`를 먼저 확정한다.

현재 확정이 필요한 항목:

- 패킷 헤더 값
- 프로토콜 버전
- 숫자 명령 ID와 상태 ID
- 체크섬 또는 CRC 알고리즘과 계산 범위
- 최대 패킷 길이
- ACK/NACK 형식
- 재시도 횟수와 응답 제한 시간
- heartbeat 주기와 통신 두절 판정
- 긴 동작 중 명령 수신 및 상태 보고 방식

### 11.1 권장 작업 순서

1. 명령과 상태 패킷의 필드 및 정확한 바이트 길이를 확정한다.
2. 모든 명령, 상태, 클러치 위치와 오류 플래그의 숫자 값을 확정한다.
3. 다중 바이트 정수의 little-endian 전송을 명시한다.
4. 체크섬 계산 범위와 검증 실패 동작을 확정한다.
5. 패킷 직렬화·역직렬화 테스트를 작성한다.
6. STM32 명령 수신 버퍼와 파서를 확장한다.
7. STM32 상태 응답 버퍼와 생성 코드를 확장한다.
8. ESP32의 명령 송신과 상태 수신 코드를 확장한다.
9. 잘못된 길이, 버전, 체크섬과 명령 ID를 시험한다.
10. `sequence` 값으로 중복 명령과 누락 응답을 검출한다.

C 구조체를 메모리 그대로 전송하면 컴파일러 패딩 문제가 생길 수 있다. 명시적인 바이트 직렬화를 사용하거나 packed 구조와 크기 검증을 함께 사용한다.

```c
_Static_assert(sizeof(CommandPacket) == EXPECTED_COMMAND_SIZE,
               "CommandPacket size mismatch");
```

프로토콜을 변경할 때 Python, ESP32와 STM32의 영향 범위 및 호환성 여부를 같은 문서에 기록한다.

## 12. 9단계: ESP32의 4개 STM32 상태 취합

단일 모듈 통신이 안정적이라고 해서 바로 `ACTIVE_LEG_COUNT = 4`로 확장하지 않는다.

### 12.1 주소별 검증 순서

```text
0x10 단독
  → 0x11 단독
  → 0x12 단독
  → 0x13 단독
  → 0x10과 0x11 동시
  → 4개 모듈 동시
```

### 12.2 ESP32가 모듈별로 관리할 정보

```text
I2C 주소
마지막 정상 응답 시각
현재 상태
활성 모터
클러치 위치
캐리어 각도
주행 RPM
동작 완료 여부
오류 플래그
통신 정상 여부
마지막 sequence
```

전체 완료 조건은 다음을 모두 만족해야 한다.

```text
4개 모듈 모두 목표 상태
AND 4개 모듈 모두 motion_complete
AND 모든 error_flags가 0
AND 모든 모듈의 최근 응답이 정상
```

한 모듈이라도 실패하면 다음을 수행한다.

```text
모든 STM32에 STOP_ALL 전송
  → 전체 상태를 FAULT로 설정
  → Python에 모듈별 원인 보고
```

모듈 간 시작 시점 동기화가 필요하면 다음 절차를 사용한다.

```text
PREPARE: 모든 STM32에 목표값 전달
  → 모든 모듈 준비 완료 확인
  → START: 모든 STM32에 실행 명령 전달
```

## 13. 10단계: Python 전체 모드 전환 UI와 상태 관리

Python은 PWM, 방향 핀 또는 클러치 구동 시간을 직접 제어하지 않고 로봇 전체의 목표만 전달한다.

권장 상위 상태:

```python
WHEEL
SWITCHING_TO_TRACK
TRACK
SWITCHING_TO_WHEEL
FAULT
```

### 13.1 UI 표시 정보

- 각 모듈의 I2C 주소와 통신 상태
- 각 STM32의 로컬 상태
- 활성 모터
- 클러치 위치
- 캐리어 각도
- 휠 또는 트랙 RPM
- 모션 완료 여부
- 오류 플래그와 사람이 읽을 수 있는 설명
- 마지막 정상 통신 시각

### 13.2 명령 처리

기존의 키 반복 전송 방식은 고정 길이 명령 패킷과 `sequence` 기반 요청·응답 구조로 변경한다.

Python의 전체 모드 전환 완료 조건:

```text
4개 STM32 모두 목표 주행 상태
AND 4개 STM32 모두 오류 없음
AND ESP32와의 통신이 정상
```

한 모듈이라도 실패하거나 통신이 끊기면 정상 주행 상태로 넘어가지 않고 `FAULT`로 이동한다.

ESC와 정지 요청은 언제든 `STOP_ALL`을 전송해야 한다. Python이 종료되거나 USB 연결이 끊어져도 ESP32와 STM32의 통신 timeout이 독립적으로 모든 모터를 정지해야 한다.

## 14. 11단계: 단일 모듈 검증 후 4개 모듈 동기화 시험

### 14.1 단일 모듈 전체 시퀀스 시험

다음 전체 루프를 낮은 출력에서 반복한다.

```text
부팅 및 원점 복귀
  → 휠 저속 주행
  → 모터1 정지 확인
  → 캐리어 트랙 목표각 정렬
  → 모터2 정지 확인
  → 클러치 b 전환 및 체결 확인
  → 트랙 저속 주행
  → 모터2 정지 확인
  → 클러치 a 전환 및 체결 확인
  → 캐리어 원점 복귀
  → 휠 주행 복귀
```

### 14.2 단일 모듈 고장 주입 시험

가능한 범위에서 안전하게 다음 조건을 시험한다.

- 엔코더 입력 연결 해제 또는 고정
- 클러치 a 센서 미입력
- 클러치 b 센서 미입력
- a와 b 센서 동시 활성
- I2C 연결 해제
- Python 프로그램 종료
- ESP32 재부팅
- 캐리어 목표각 미도달
- 모터 구속 또는 과전류 조건 모사
- 각 전환 단계에서 `STOP_ALL` 입력

각 시험에서 모든 모터가 정지하고 올바른 오류 플래그가 설정되는지 확인한다.

### 14.3 4개 모듈 시험 순서

1. 모터 전원을 차단한 상태에서 네 STM32의 주소 충돌 여부를 확인한다.
2. 네 STM32의 상태 패킷을 반복 조회한다.
3. 모듈별 센서값과 초기화 상태를 비교한다.
4. 모든 모터 출력이 0인 상태에서 상태 전이 명령만 시험한다.
5. 무부하·저출력으로 단일 모터 종류별 동시 구동을 시험한다.
6. 네 모듈의 전체 모드 전환을 시험한다.
7. 제한된 하중에서 시험한다.
8. 결과가 안정된 뒤 실제 운용 조건으로 범위를 확대한다.

### 14.4 측정할 값

- 각 모듈의 전환 시작 시각과 완료 시각
- 모듈 간 완료 시간 편차
- 캐리어 목표각 오차
- 휠 또는 트랙 RPM 편차
- I2C 전송 및 수신 실패 횟수
- 모터별 최대 전류
- 각 단계 timeout 발생 여부
- 비상 정지 후 실제 정지시간

현재 단일 모듈에서 안정화된 ESP32의 100ms 폴링 주기와 I2C write 후 read 전 20ms 대기는 초기 다중 모듈 시험에서도 유지한다. 네 모듈에서 충분한 측정 근거가 확보된 뒤에만 주기를 줄인다.

## 15. 단계별 공통 완료 절차

## 16. 지금 바로 시작할 작업

현재 프로젝트에서 바로 시작할 작업은 **1단계 센서 입력 검증**이다.

실행 순서:

1. `feature/sensor-feedback-control` 브랜치를 만든다.
2. 모터1 엔코더의 데이터시트 PPR 또는 CPR과 감속비를 확인한다.
3. 현재 코드에서 모터1 출력축 1회전당 실제 카운트를 측정한다.
4. 모터2 엔코더와 캐리어 원점 센서의 부품 및 핀을 결정한다.
5. 클러치 a/b 센서의 부품, 설치 위치와 핀을 결정한다.
6. `mobility.ioc`에 센서 입력 핀을 배치한다.
7. 센서 입력만 읽어 상태를 확인할 수 있는 코드를 구현한다.
8. 모터별 정·역방향과 센서 카운트 부호를 검증한다.
9. 측정값, 센서 논리와 배선표를 문서화한다.
10. 모든 센서 입력을 신뢰할 수 있을 때 2단계 환산 코드로 넘어간다.

PID 제어를 먼저 작성하지 않는다. 엔코더 CPR, 감속비, 캐리어 원점과 클러치 a/b 위치 입력이 확정되어야 제어기가 물리적으로 의미 있는 각도와 RPM을 사용할 수 있다.
