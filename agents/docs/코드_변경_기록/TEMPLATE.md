# YYYYMMDD_HHMMSS 변경 제목

## 1. 기록 정보

| 항목 | 내용 |
|---|---|
| 작업 시작 시각 | YYYY-MM-DD HH:MM:SS KST |
| 작업 종료 시각 | YYYY-MM-DD HH:MM:SS KST 또는 진행 중 |
| 작업 브랜치 | 브랜치 이름 |
| 기준 Git 커밋 | 커밋 해시 또는 미확인 |
| 작성자 | 이름 또는 작업 주체 |

## 2. 변경 목적

- 해결하려는 문제 또는 추가하려는 기능을 적는다.
- 이 변경이 필요한 이유를 적는다.

## 3. 변경 전 동작

- 변경 전 시스템이 실제로 어떻게 동작했는지 적는다.
- 재현 조건이나 기존 한계가 있으면 함께 적는다.

## 4. 수정 파일

| 파일 | 변경한 함수·심볼·설정 | 변경 유형 |
|---|---|---|
| `경로` | 함수 또는 설정 이름 | 추가/수정/삭제 |

## 5. 상세 변경 내용과 이유

### 5.1 변경 항목

- 무엇을 어떻게 바꾸었는지 적는다.
- 숫자 상수에는 단위와 선정 근거를 적는다.
- 중요한 변경 전후 흐름을 필요한 만큼 설명한다.

## 6. 영향 범위

| 영역 | 영향 | 설명 |
|---|---|---|
| Python/PC | 있음/없음 | 근거 |
| ESP32 | 있음/없음 | 근거 |
| STM32 | 있음/없음 | 근거 |
| 공용 프로토콜 | 있음/없음 | 근거 |
| 하드웨어·배선 | 있음/없음 | 근거 |

## 7. 프로토콜 호환성

- 패킷 길이, 명령·상태 ID, 단위, 바이트 순서의 변경 여부를 적는다.
- 호환되지 않는 변경이면 프로토콜 버전과 관련 구성요소의 동시 수정 내용을 적는다.
- 변경이 없으면 `프로토콜 변경 없음`과 근거를 적는다.

## 8. 안전 영향과 정지 동작

- 모터 정지 조건, timeout, 인터록에 미치는 영향을 적는다.
- 센서·통신 오류 시 출력이 어떻게 되는지 적는다.
- 안전 영향이 없으면 그 근거를 적는다.

## 9. 수행한 검증

| 검증 항목 | 방법 또는 명령 | 결과 |
|---|---|---|
| 정적 검사/문법 검사 | 명령 | 성공/실패와 핵심 출력 |
| 빌드 | 대상과 설정 | 성공/실패 또는 미수행 |
| 단위 테스트 | 테스트 이름 | 성공/실패 또는 미수행 |
| 실기 시험 | 보드·배선·부하 조건 | 성공/실패 또는 미수행 |

## 10. 확인하지 못한 항목

- 컴파일, 플래시 또는 실기 시험 중 수행하지 못한 항목을 적는다.
- 확인하지 않은 기능을 완료로 표현하지 않는다.

## 11. 되돌리기 방법

- 문제가 생겼을 때 어떤 파일 또는 설정을 되돌려야 하는지 적는다.
- 데이터나 프로토콜 호환성에 별도 복구 절차가 있으면 적는다.

## 12. 남은 위험과 후속 작업

- 아직 해결되지 않은 위험을 적는다.
- 다음 작업에서 확인할 항목과 우선순위를 적는다.
