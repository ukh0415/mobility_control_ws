# 모터2 PB3/PB5 엔코더 읽기 추가

## 발생 시각과 환경
2026-09-07 12:21 KST, STM32F103C8T6 + ESP32(esp32:esp32:esp32), USB 시리얼 PC 클라이언트.
사용자 배선: 모터2 ENA=PB3, ENB=PB5.

## 사용한 코드 버전 또는 Git 커밋
기준 f1a0b5d, 작업 브랜치 feature/motor2-encoder.
기존 .settings/language.settings.xml 사용자 변경은 유지했다.

## 증상
모터2 엔코더를 읽는 코드와 핀 초기화가 없었다.

## 재현 절차
기존 main.c의 EXTI 콜백과 GPIO 초기화를 확인하면 PA4/PA5만 처리한다.

## 기대 동작
모터2의 회전 방향에 따라 독립 카운트가 증감하고 PC 시리얼 로그에 표시된다.

## 조사 내용과 측정값
- PA4/PA5는 기존 바퀴 엔코더이며 그대로 유지한다.
- PB3은 기존 HAL_MspInit의 SWJ_NOJTAG 설정으로 GPIO 사용 가능하고 SWD는 유지된다.
- PB3 상승 에지/EXTI3에서 PB5를 판독하는 x1 계수: Low=+1, High=-1.
- motor2_encoder_count는 부팅 시 0이며 int32 경계에서 명시적으로 순환한다.
- GPIO는 기존 엔코더와 같은 NOPULL이다. 출력 전압/출력 방식, PPR, 감속비는 미확정이다.
- 실제 전압, 파형, 카운트 측정은 수행하지 않았다.

## 원인
소스상 모터2 엔코더 처리 누락. 실물 신호 정상 여부는 미확정.

## 해결 또는 임시 조치
- main.h 핀 정의, main.c GPIO/카운터/패킷, stm32f1xx_it.c EXTI3 핸들러 추가.
- mobility.ioc에 PB3=GPXTI3, PB5=GPIO_Input 반영.
- EXTI3 NVIC 활성화와 IRQ 핸들러는 USER CODE 영역에서 직접 관리한다.
  CubeMX NVIC에서 별도 코드 생성을 켜면 핸들러 중복 여부를 확인해야 한다.
- protocol/protocol.md에 버전 2의 8바이트 진단 응답을 먼저 정의했다.
- ESP32는 응답 길이/버전을 검사하고 motor2_count를 USB 로그에 출력한다.
  Python은 기존 그대로 로그를 출력한다. TCP STATUS 형식은 유지한다.
- STM32와 ESP32를 함께 빌드·업로드해야 한다.

## 검증 결과
- STM32: ARM GCC 13.3.1, Cortex-M3 / STM32F103xB로 Core, HAL, startup 전체 컴파일 및
  저장소 STM32F103C8TX_FLASH.ld를 사용한 링크 성공. 임시 폴더에 산출했다.
- 변경 C 파일 -Wall -Wextra 구문 검사 통과. git diff --check 통과.
- CubeIDE 생성 makefile에 과거 M: 경로가 있어 검증은 별도 GCC 호출로 수행했다.
- ESP32: Arduino CLI, esp32:esp32:esp32 컴파일 성공. Flash 923304 bytes (70%),
  RAM 48160 bytes (14%). 최초 sandbox 접근 제한 후 권한을 갖춰 재실행하여 통과했다.
- 플래시 대상은 저장소 stm32/mobility의 STM32F103C8T6. 업로드 및 실기 시험은 수행하지 않았다.

## 남은 위험과 후속 작업
1. 모터 전원을 끄고 로직 전원만 켠 상태에서 축을 움직여 motor2_count의 증감 확인.
2. 분해능, 감속비, 신호 전압과 출력 방식을 확인하고 필요하면 풀업 등 입력 회로를 맞춘다.
3. 고속에서는 EXTI 지연으로 펄스 누락 가능하므로 파형/실제 회전수와 비교한다.
4. 기존 angle 값은 PA4/PA5 카운트의 나머지이며 보정 각도가 아니다.
5. 이번 변경은 진단 계수 추가이며 정지 판정/위치 제어에 아직 사용하지 않는다.
   기존 독립 모터 제어에는 로컬 인터록/통신 watchdog이 완성되지 않아 자동 전환 시험 전에 보강이 필요하다.

## 2026-09-07 후속 기록: 구성요소별 상세 변경 내역

아래 행 번호는 기록 시점의 소스 기준이다. 파일 경로는 저장소 루트 기준이다.
이번 후속 작업은 문서 보강이며 소스 코드를 추가 수정하지 않았다.

### 1. STM32 핀과 핀 정의

| 대상 | 핀 | 설정 | 변경 여부 |
|---|---|---|---|
| 모터2 ENA | PB3 | GPIO_MODE_IT_RISING, GPIO_NOPULL | 신규. 상승 에지마다 EXTI3 발생 |
| 모터2 ENB | PB5 | GPIO_MODE_INPUT, GPIO_NOPULL | 신규. ENA 상승 순간의 방향 판별 |
| 모터2 인터럽트 | EXTI3_IRQn | 우선순위 (5, 0), IRQ 활성화 | 신규. PB5에는 인터럽트 사용 안 함 |
| 기존 바퀴 ENA/ENB | PA4/PA5 | 기존 EXTI4 상승 에지/일반 입력 | 변경 없음 |
| 디버그 기능 | PB3 JTAG 기능 해제 | SWJ_NOJTAG | 기존 설정 사용, SWD 유지 |

`stm32/mobility/Core/Inc/main.h:69`의 `USER CODE BEGIN Private defines`에 추가:

```c
#define MOTOR2_ENC_A_Pin GPIO_PIN_3
#define MOTOR2_ENC_A_GPIO_Port GPIOB
#define MOTOR2_ENC_B_Pin GPIO_PIN_5
#define MOTOR2_ENC_B_GPIO_Port GPIOB
```

ENA/ENB는 엔코더 입력이다. 모터2 PWM=PA8(TIM1_CH1), DIR=PB1/PB10,
j/l 구동 명령 처리는 이번에 변경하지 않았다.

### 2. STM32 main.c 변경 상세

파일: `stm32/mobility/Core/Src/main.c`

| 위치 | 이전 | 변경 후 / 목적 |
|---|---|---|
| 55행, USER CODE PV | i2c_tx_buf[3] | i2c_tx_buf[8]: 버전과 모터2 계수 추가 공간 |
| 61행, USER CODE PV | 모터2 변수 없음 | volatile int32_t motor2_encoder_count = 0 추가 |
| 146행, PrepareStatusBuffer() | mode/angle 3바이트 | 버전 1바이트, count 4바이트 추가 |
| HAL_I2C_AddrCallback(), 166행 | 송신 길이 상수 3 | sizeof(i2c_tx_buf)로 8바이트 송신 |
| 189행, HAL_GPIO_EXTI_Callback() | PA4 바퀴 엔코더 처리만 존재 | PB3 분기 추가, PB5로 증감 방향 판별 |
| 581행, MX_GPIO_Init()의 USER CODE MX_GPIO_Init_2 | 모터2 입력 설정 없음 | PB5 입력, PB3 인터럽트, EXTI3 NVIC 설정 추가 |

**계수 동작:** PB3 상승 순간 PB5가 Low이면 +1, High이면 -1이다.
A 상승 에지만 세는 x1 방식이며 A/B 양쪽의 모든 에지를 세는 x4 방식은 아니다.
부호와 실제 기구 정회전의 관계는 실기로 확인해야 한다.
INT32_MAX에서 증가하면 INT32_MIN, INT32_MIN에서 감소하면 INT32_MAX로
명시적으로 순환시켜 signed overflow를 피한다. 부팅하면 0부터 시작한다.
`volatile`은 인터럽트에서 변하는 값을 나타낸다.

**패킷 구성:** PrepareStatusBuffer()는 계수를 한 번 읽어 uint32_t motor2_snapshot에
저장한 후 바이트로 나눈다. 각 바이트 생성 중 카운트를 다시 읽지 않으며,
음수도 32비트 비트 패턴으로 little-endian 전송한다.

**GPIO 초기화 순서:** PB5를 INPUT/NOPULL로 초기화하고 PB3를 IT_RISING으로
초기화한 다음 HAL_NVIC_SetPriority(EXTI3_IRQn, 5, 0)과
HAL_NVIC_EnableIRQ(EXTI3_IRQn)를 호출한다. PB3도 NOPULL을 사용한다.

**main()의 while 루프:** 모터2 폴링 코드는 추가하지 않았다. 기존 MX_GPIO_Init()
호출로 초기화되고 인터럽트에서 누적한다. 기존
`carrierAngleTenths = (int16_t)(encoderCount % 32000)`는 그대로이며
모터2 계수와 연결하지 않았다. 이 기존 angle은 실제 각도로 보정된 값이 아니다.

### 3. STM32 IRQ 파일과 CubeMX 설정

`stm32/mobility/Core/Src/stm32f1xx_it.c:244`, USER CODE BEGIN 1에 추가:

```c
void EXTI3_IRQHandler(void)
{
  HAL_GPIO_EXTI_IRQHandler(MOTOR2_ENC_A_Pin);
}
```

호출 순서는 PB3 상승 → EXTI3_IRQHandler → HAL_GPIO_EXTI_IRQHandler →
HAL_GPIO_EXTI_Callback → motor2_encoder_count 갱신이다.
startup 파일에는 기존 EXTI3 벡터가 있어 수정하지 않았다.

`stm32/mobility/mobility.ioc` 변경:

- Mcu.Pin20=PB3, Mcu.Pin21=PB5 추가, Mcu.PinsNb=20에서 22로 변경.
- PB3.Locked=true, PB3.Signal=GPXTI3 추가.
- PB5.Locked=true, PB5.Signal=GPIO_Input 추가.
- SH.GPXTI3.0=GPIO_EXTI3, SH.GPXTI3.ConfNb=1 추가.

EXTI3 NVIC 코드 생성 설정은 추가하지 않았다. IRQ 활성화와 핸들러는 위 USER CODE에서
직접 관리하므로 현재 소스 빌드에는 IDE의 추가 핀 설정이 필요 없다.
CubeMX 재생성 시 USER CODE 보존을 유지하고 PB3/PB5 최종 초기화를 확인한다.
NVIC에서 EXTI3 코드 생성을 별도로 켜면 IRQ 핸들러 중복 여부를 확인해야 한다.

`stm32/mobility/Core/Src/stm32f1xx_hal_msp.c:79`의
`__HAL_AFIO_REMAP_SWJ_NOJTAG()`는 원래 있던 설정이며 수정하지 않았다.

### 4. STM32 → ESP32 패킷과 공용 규격

`protocol/protocol.md` 문서 버전은 0.1.0-draft에서 0.2.0-draft로 변경했다.
현재 구현의 진단 패킷 버전은 바이트3에 숫자 2를 기록한다.

| 바이트 | 자료형 / 값 | 의미 |
|---|---|---|
| 0 | uint8 | 기존 currentMode |
| 1–2 | int16 little-endian | 기존 carrierAngleTenths |
| 3 | uint8, 2 | 진단 패킷 버전 |
| 4–7 | int32 little-endian | motor2_encoder_count, 단위 count |

count=123이면 바이트4–7은 7B 00 00 00, count=-1이면 FF FF FF FF다.
명령 1문자와 I2C 주소 0x10~0x13은 유지한다. 응답 길이가 변경되어
STM32와 ESP32를 함께 업데이트해야 한다.

### 5. ESP32 변경 상세

파일: `esp32/esp32_i2c_master/esp32_i2c_master.ino`

| 위치 | 변경 내용 |
|---|---|
| 상단 패킷 설명 | 3바이트에서 8바이트로 변경, version/count 배치 설명 추가 |
| 47행, LegStatus | int32_t motor2_encoder_count 멤버 추가 |
| 58행, readStatusFromLeg() | Wire.requestFrom 요청 길이를 3에서 8로 변경 |
| 같은 함수 길이 검사 | 정확히 8바이트가 아니면 잔여 수신 바이트를 비우고 false 반환 |
| 68행부터 | 버전과 count 4바이트를 읽고 little-endian uint32로 조립 |
| 73행 | version != 2이면 false 반환 |
| 74행 | uint32 비트 패턴을 음수까지 보존하는 int32 계수로 복원 |
| 124행, printStatusToSerial() | 정상 응답일 때 motor2_count=와 계수 출력 추가 |

기존 pollAllLegs()가 반환값을 legs[i].ok에 저장한다. 길이/버전 오류면 ok=false가
되어 그 사이클의 카운트는 출력하지 않는다. 기존 bytesReceived 진단 값에서
8바이트 수신 여부를 확인할 수 있다.

표시 예시(실제 측정 로그 아님):

```text
leg[0] addr=0x10 ok=true mode=0 angle=0.0 motor2_count=123  |
```

ESP32 핀 설정은 변경하지 않았다. 기존 GPIO21=SDA, GPIO22=SCL을 사용한다.
모터2 ENA/ENB는 STM32 PB3/PB5에 연결되며 ESP32에 직접 연결하지 않는다.
기존 ACTIVE_LEG_COUNT=1, POLL_INTERVAL_MS=100도 유지하여 현재 0x10 한 모듈을
약 100ms 주기로 조회한다. STM32는 그 사이에도 인터럽트로 계속 계수한다.

sendStatusToClient()의 WiFi/TCP STATUS 형식은 변경하지 않았다.
**새 모터2 계수는 USB 시리얼 로그에 표시되며 TCP STATUS에는 포함되지 않는다.**
기존 명령 라우팅과 failsafe 시간도 수정하지 않았다.

### 6. Python 수정 여부와 기존 표시 경로

파일: `pc/robot_control_client_serial.py`. **이번 기능 추가에서 Python 코드 수정은 없다.**
기존 프로그램이 ESP32 로그 한 줄 전체를 출력하므로 새 필드가 자동으로 표시된다.

| 기존 위치 | 코드 / 역할 |
|---|---|
| 86행, status_receiver() | 시리얼 상태/디버그 줄 수신 루프 |
| 95행 | line = s.readline(): 한 줄 수신 |
| 101행 | print(line.decode("ascii", errors="ignore").rstrip()): 수신 줄 출력 |
| 161행, main() | status_receiver를 백그라운드 스레드로 실행 |

motor2_count는 ASCII이므로 기존 디코딩으로 표시된다. Python에서 별도 카운트 변수에
저장하거나 각도 계산, 그래프, 파일 기록을 하는 기능은 추가하지 않았다.
포트 설정, 전송 속도, 제어 키와 재전송 주기도 변경하지 않았다.

전체 데이터 경로:

```text
모터2 ENA/ENB → STM32 PB3/PB5 → EXTI3 → motor2_encoder_count
→ PrepareStatusBuffer()의 8바이트 I2C 응답
→ ESP32 readStatusFromLeg() → printStatusToSerial()
→ USB Serial → Python status_receiver() → 콘솔 motor2_count 표시
```
