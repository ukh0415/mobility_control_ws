# TIM 하드웨어 엔코더 전환의 장점과 핀맵 설계안

## 1. 판단과 권장안

**모터1·2를 모두 하드웨어 엔코더로 전환한다면, TIM2·TIM3를 각각 엔코더 전용으로 쓰고 모터1·2·3의 PWM을 TIM1의 세 채널로 모으는 구성을 권장한다.**

현재처럼 펄스마다 CPU가 인터럽트를 처리하는 부담을 줄이고, A/B 위상에 따른 계수를 타이머가 수행하도록 만들 수 있다. 다만 핀 이동뿐 아니라 PWM 채널 재배치, 16비트 카운터 누적, x1→x4 단위 변경까지 함께 설계해야 한다.

| 기능 | 현재 | 권장안 |
|---|---|---|
| 모터1 엔코더 A | PA4, EXTI4 | **PA15, TIM2_CH1** |
| 모터1 엔코더 B | PA5, GPIO 입력 | **PB3, TIM2_CH2** |
| 모터2 엔코더 A | PB3, EXTI3 | **PB4, TIM3_CH1** |
| 모터2 엔코더 B | PB5, GPIO 입력 | **PB5, TIM3_CH2**: 배선 유지 |
| 모터1 PWM | PA6, TIM3_CH1 | **PA9, TIM1_CH2** |
| 모터2 PWM | PA8, TIM1_CH1 | **PA8, TIM1_CH1**: 유지 |
| 모터3 PWM | PA2, TIM2_CH3 | **PA10, TIM1_CH3** |

이 안은 **엔코더 신호선 3개와 PWM 신호선 2개, 총 5개의 신호 연결을 옮기는 안**이다. 전원·GND선을 포함한 커넥터 핀 수를 뜻하지 않는다. 모터 방향 6개 핀, 모듈 주소 입력, I2C와 SWD는 유지한다.

**상태: 검토용 설계안이며 미적용이다. 이번 작업에서는 이 문서만 추가하며 C 코드, `.ioc`, 공용 프로토콜과 실제 배선을 변경하지 않는다.**

## 4. GPIO/EXTI 방식과 TIM Encoder Mode의 차이

현재도 입력은 GPIO 핀을 통해 들어오고, TIM 방식으로 바꿔도 물리 입력은 GPIO 핀이다. 차이는 **그 신호를 CPU의 EXTI 콜백이 해석하는가, 타이머의 엔코더 회로가 해석하는가**다.

```text
현재:
A 상승 → EXTI → CPU 콜백 → B를 GPIO로 읽음 → 소프트웨어 변수 ±1

권장:
A/B → TIM CH1/CH2 입력 → 하드웨어 위상 판정 → TIMx_CNT 증감
                                      ↓
                         CPU는 정해진 주기에 CNT를 읽어 누적·속도 계산
```

| 항목 | 현재 EXTI x1 | 권장 TIM Encoder TI12 x4 |
|---|---|---|
| 펄스 처리 주체 | CPU 콜백 | 타이머 하드웨어 |
| CPU 실행 빈도 | A 상승마다 인터럽트 | 예: 1 ms마다 누적값 갱신; 최종 주기는 최대 속도로 결정 |
| 방향 판정 | 인터럽트 실행 시 B 읽음 | 타이머 입력 경로에서 A/B 위상 처리 |
| 분해능 | A 한 주기에 1 count | A/B 한 주기에 4 counts |
| 입력 필터 | 현재 별도 구현 없음 | `IC1Filter`, `IC2Filter` 설정 가능 |
| 계수 저장 | 소프트웨어 int32 | 하드웨어 16비트 CNT + 소프트웨어 누적 |
| 핀 자유도 | 일반 EXTI 입력 선택 가능 | 같은 타이머 CH1/CH2 핀 쌍 필요 |
| 자원 비용 | EXTI·CPU 시간 | 엔코더마다 타이머 한 개의 계수 자원 |

TI1/TI2는 x2, TI12는 x4임을 저장소 ST HAL의 [stm32f1xx_hal_tim.h](../../stm32/mobility/Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_tim.h) `TIM_Encoder_Mode` 정의에서 확인했다. TI1 모드를 현재 x1과 동일하다고 간주하면 안 된다.

### 이 프로젝트에서 얻는 장점

1. **통신 인터럽트와 엔코더 처리의 경쟁을 줄인다.** 현재 I2C IRQ 우선순위는 0, EXTI3/4는 5다. CPU가 I2C를 처리하는 동안에도 클록이 동작하는 타이머는 입력을 계수하므로, EXTI 콜백 지연 때문에 에지를 놓치는 위험을 줄인다.
2. **B를 늦게 읽어서 방향이 달라지는 문제를 줄인다.** 현재는 A 상승 후 콜백 실행까지 지연이 있다. TIM 방식은 소프트웨어 GPIO 읽기 지연에 의존하지 않는다.
3. **CPU 사용량을 예측하기 쉬워진다.** 예를 들어 각 센서 A가 10 kHz면 현재 두 모터 합계 약 20,000회의 EXTI 처리가 필요하다. TIM 방식은 이를 하드웨어에 맡기고 두 CNT를 일정 주기에 읽을 수 있다. 이 수치는 설명용 가정이며 실제 부하 측정은 아니다.
4. **작은 움직임을 더 세밀하게 기록한다.** x4 계수로 이상적인 회전당 카운트는 현재의 4배가 된다. 센서 자체 정확도·기어 백래시까지 4배 개선된다는 뜻은 아니다.
5. **짧은 잡음 펄스를 거르는 입력 필터를 사용할 수 있다.** 필터를 강하게 설정하면 정상 고속 펄스도 사라질 수 있으므로 파형을 보고 결정한다.

타이머도 무제한 속도로 읽지는 못한다. 신호 전압, 에지 품질, 필터와 타이머 입력 타이밍 한계는 남는다. 계수가 멈췄다는 사실만으로 실제 정지와 센서 단선을 구분하지도 못한다.

## 5. 왜 현재 핀 그대로는 안 되는가?

### PA4/PA5와 PB3/PB5의 제약

- 모터1 PA4/PA5에는 이 칩의 TIM 엔코더용 CH1/CH2 쌍이 없다.
- PB3은 리맵 시 TIM2_CH2, PB5는 리맵 시 TIM3_CH2다. **서로 다른 타이머의 CH2 두 개를 하나의 Encoder Mode 입력 쌍으로 묶을 수 없다.**
- 엔코더 한 개는 같은 TIM의 CH1과 CH2에 연결해야 한다. CH3/CH4 두 개를 두 번째 엔코더 입력으로 쓰는 구성도 지원하지 않는다.

핀 기능은 [ST 데이터시트 DS5319 Rev 20, 표 5](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)의 PA4/PA5, PA15, PB3/PB4/PB5 항목으로 확인했다. 채널 제약은 저장소 [HAL_TIM_Encoder_Init()](../../stm32/mobility/Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_tim.c)의 설명과 구현으로 확인했다.

### “TIM2 CH1/CH2는 엔코더, CH3는 기존 PWM”이 안 되는 이유

현재 모터3 PWM이 TIM2_CH3에 있으므로 CH1/CH2만 엔코더로 바꾸면 될 것처럼 보인다. 그러나 **CH1~CH4는 같은 TIM2_CNT와 시간 기준을 공유한다.**

엔코더 모드에서는 CNT가 엔코더 움직임에 따라 증가·감소한다. 이 CNT로 CH3 PWM을 만들면 일정 시간 간격의 1 kHz 출력이 되지 않는다. 따라서 독립적인 모터 구동 PWM은 다른 타이머로 옮겨야 한다. CH3/CH4에 가능한 다른 비교 기능이 있다는 사실과 고정 주파수 PWM을 유지할 수 있다는 것은 다르다.

같은 이유로 TIM3를 모터2 엔코더로 사용하면 기존 모터1의 TIM3_CH1 PWM을 옮겨야 한다.

## 6. 타이머 후보 검토

| 타이머 | 사용할 수 있는 대표 CH1/CH2 쌍 | 현재 충돌 | 판단 |
|---|---|---|---|
| TIM1 | PA8 / PA9 | PA8 모터2 PWM | 사용 가능하나 PWM 배치를 더 크게 재설계해야 함 |
| TIM2 기본 | PA0 / PA1 | 모듈 주소 입력 2개 | 주소 핀 이동이 필요해 우선순위 낮음 |
| TIM2 Partial Remap 1 | **PA15 / PB3** | PB3 모터2 A; TIM2는 모터3 PWM 사용 중 | **모터1 엔코더로 권장** |
| TIM3 기본 | PA6 / PA7 | 모터1 PWM / DIR | 방향선까지 이동하므로 우선순위 낮음 |
| TIM3 Partial Remap | **PB4 / PB5** | PB5는 기존 모터2 B; TIM3는 모터1 PWM 사용 중 | **모터2 엔코더로 권장** |
| TIM4 기본 | PB6 / PB7 | I2C1 SCL / SDA | 통신 배선 이동이 필요해 우선순위 낮음 |
| TIM3 Full Remap | PC6 / PC7 | LQFP48에 핀 없음 | 이 패키지에서 사용 불가 |
| TIM4 Remap | PD12 / PD13 | LQFP48에 핀 없음 | 이 패키지에서 사용 불가 |

리맵 조합은 저장소 [stm32f1xx_hal_gpio_ex.h](../../stm32/mobility/Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_gpio_ex.h)의 TIM2/TIM3/TIM4 리맵 정의를 근거로 한다. 패키지 핀 존재 여부는 [DS5319 표 5의 LQFP48 열](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)과 대조했다.

TIM4가 주변장치로 비어 있어도 기본 CH1/CH2 핀이 I2C에 사용 중이므로 엔코더에 바로 추가할 수 없다. 권장안에서는 TIM4를 내부 주기 작업용 후보로 남겨둘 수 있다. 내부 시간 기준으로만 쓴다면 외부 CH 핀을 배정할 필요가 없다.

| 모터1 PWM | PA9 | TIM1_CH2, PWM | PA6에서 이동 |
| 모터1 DIR1 / DIR2 | PA7 / PB0 | GPIO Output | 유지 |
| 모터2 PWM | PA8 | TIM1_CH1, PWM | 유지 |
| 모터2 DIR1 / DIR2 | PB1 / PB10 | GPIO Output | 유지 |

| 모터3 DIR1 / DIR2 | PB8 / PB9 | GPIO Output | 유지 |
| 모듈 주소 bitA / bitB | PA0 / PA1 | GPIO Input, Pull-up | 유지 |
| I2C1 SCL / SDA | PB6 / PB7 | I2C1 | 유지 |
| SWDIO / SWCLK | PA13 / PA14 | Serial Wire | 유지 |
| 외부 HSE | PD0 / PD1 | OSC_IN / OSC_OUT | 유지 |

PA2/PA4/PA5/PA6은 이 배치에서 기존 기능을 해제한다. 새 용도는 아직 배정하지 않는다. PA11/PA12도 이번 제안에서는 사용하지 않는다.

**주의할 배선 전환:** PB3의 기존 모터2 A선을 PB4로 옮긴 뒤 PB3에는 모터1 B선을 연결하는 구조다. 두 센서 출력을 PB3에 동시에 연결하는 것이 아니다.

### 필요한 리맵과 디버그 설정

```c
// 아래는 향후 구현 시 필요한 설정을 나타낸 예시이며 현재 적용하지 않음.
__HAL_AFIO_REMAP_TIM2_PARTIAL_1();  // CH1=PA15, CH2=PB3
__HAL_AFIO_REMAP_TIM3_PARTIAL();   // CH1=PB4,  CH2=PB5
__HAL_AFIO_REMAP_SWJ_NOJTAG();     // JTAG 해제, SWD 유지
```

기존 `HAL_MspInit()`에 NOJTAG가 이미 있다. 새 배정에서는 PA15/PB3/PB4 모두 JTAG에서 해제되어야 하며, 리맵 적용 후에도 SWD가 유지되는지 확인한다. PB3을 엔코더에 사용하므로 SWO trace 출력과 병용하지 않는다.

TIM3 Partial Remap에 PB0/PB1의 CH3/CH4 대체 기능도 표시되지만 두 채널을 활성화하지 않고 PB0/PB1을 GPIO 출력으로 유지하면 기존 방향 핀을 사용할 수 있다. CubeMX가 이를 AF 출력으로 바꾸지 않았는지 최종 생성 코드를 확인한다. TIM2 Partial Remap 1을 명시적으로 선택해 불필요한 전체 리맵을 피한다.

### PWM을 TIM1에 모아도 모터별 속도는 따로 제어할 수 있는가?

가능하다. 주파수는 공통이지만 각 채널은 별도 비교값 CCR1/CCR2/CCR3를 사용하므로 듀티 비율은 독립적으로 바꿀 수 있다.

```text
TIM1 공통 PSC/ARR → 같은 PWM 주파수
  CH1 / CCR1 / PA8  → 모터2 듀티
  CH2 / CCR2 / PA9  → 모터1 듀티
  CH3 / CCR3 / PA10 → 모터3 듀티
```

현 설정 72 MHz, PSC=71, ARR=999를 유지하면 계산상 1 kHz다. 현재도 세 타이머가 같은 값이므로 PWM 통합이 적합하다고 판단했다. 향후 모터마다 다른 PWM 주파수가 필요해지면 이 배치를 재검토해야 한다. 한 모터 정지 시 TIM1 전체를 정지시키거나 MOE를 끄지 말고 해당 채널 듀티와 방향 출력을 처리해야 한다.

PA9/PA10은 USART1 기본 TX/RX와 겹친다. 현재 소스에는 STM32 USART1 사용이 없으므로 채택했지만 향후 UART 추가 시 다른 핀·주변장치를 검토해야 한다. TIM1의 PA8/PA9/PA10 채널 배정은 [DS5319 표 5](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)로 확인했다.

## 8. 대안과 권장안 선택 이유

| 안 | 주요 변경 | 장점 | 단점 / 선택 조건 |
|---|---|---|---|
| **권장: 두 엔코더 TIM2/TIM3, PWM TIM1 통합** | 신호선 5개 이동 | 주소·I2C·방향선 유지, 두 엔코더 방식 통일 | PWM 주파수 공유, 두 리맵 필요 |
| 모터2만 먼저 TIM3 PB4/PB5로 전환 | 모터2 A PB3→PB4, 모터1 PWM PA6→PA9(TIM1_CH2), 총 2개 이동 | 단계적으로 검증 가능, 모터3 PWM PA2 유지 | 모터1은 EXTI로 남음 |
| TIM2 기본 PA0/PA1 + TIM3 PB4/PB5 | 주소선도 빈 GPIO로 이동 필요 | TIM2 리맵 불필요 | 모듈 주소 읽기 코드·배선까지 영향 확대 |
| TIM4 PB6/PB7 사용 | I2C 핀과 필요 시 방향 핀 재배치 | TIM4 계수 자원 사용 | 통신과 클러치 배선에 영향; 권장하지 않음 |

권장안은 가능한 모든 배선의 전역 최적해를 주장하는 것이 아니라, **현재 주소·I2C·방향선을 유지하고 두 엔코더를 같은 방식으로 통일한다는 기준에서 선택한 안**이다. 실제 커넥터 접근성이나 PCB가 고정되어 있으면 배선 작업량은 달라진다.

## 9. 향후 CubeMX/HAL 설정 초안

다음은 구현 승인 후 적용할 초안이다. 특히 필터와 갱신 주기는 센서 최대 주파수 확인 전 확정하지 않는다.

| 설정 | TIM2: 모터1 / TIM3: 모터2 제안 |
|---|---|
| Combined Channels | Encoder Mode, TI1 and TI2 |
| `EncoderMode` | `TIM_ENCODERMODE_TI12` (x4) |
| `Prescaler` | 0: PWM의 71을 복사하지 않음 |
| `Period` | 65535 (`0xFFFF`): 16비트 전체 범위 |
| `CounterMode` | `TIM_COUNTERMODE_UP` 초기값; 실제 증감 방향은 엔코더 모드에서 결정 |
| `ClockDivision` | `TIM_CLOCKDIVISION_DIV1` 초안 |
| `AutoReloadPreload` | DISABLE 초안 |
| `IC1Selection`, `IC2Selection` | `TIM_ICSELECTION_DIRECTTI` |
| `IC1Prescaler`, `IC2Prescaler` | `TIM_ICPSC_DIV1` |
| `IC1Polarity`, `IC2Polarity` | `TIM_ICPOLARITY_RISING` 비반전 기준 초안 |
| `IC1Filter`, `IC2Filter` | 같은 값으로 시작, 파형·속도에 맞춰 확정 |
| 시작 | `HAL_TIM_Encoder_Start(&htim2, TIM_CHANNEL_ALL)` 및 htim3 |
| 읽기 | `__HAL_TIM_GET_COUNTER(&htim2)` 및 htim3 |
| EXTI | 엔코더용 EXTI3/4 비활성화 및 기존 증감 분기 제거 예정 |

`ICxPolarity=RISING`이라는 이름을 보고 x1이라고 해석하면 안 된다. 엔코더 TI12의 x4 동작과 입력 극성 설정은 별개다. 부호가 기존 Low=+1 규칙과 일치하는지는 실제 정·역방향으로 확인하고 방향 보정 상수를 적용한다.

정상 계수에 `HAL_TIM_Encoder_Start_IT()`로 매 캡처 인터럽트를 받을 필요는 없다. 일반 Start 후 주기적으로 CNT를 읽는 안을 우선 검토한다. 이 함수는 시작 설정 후 반환하며 CPU가 펄스를 기다리는 루프를 돌지 않는다. 오버플로 인터럽트를 별도로 사용하는 대안을 택하면 update interrupt 설정과 경계 경쟁 처리가 추가로 필요하다.

STM32F1 입력은 타이머에 연결되어도 GPIO 초기화 코드가 `GPIO_MODE_INPUT` 형태일 수 있다. 출력용 `GPIO_MODE_AF_PP`를 엔코더 입력에 적용하지 않는다. Pull은 센서 출력 방식에 맞추며 현재 NOPULL을 확인 없이 정답으로 고정하지 않는다. 근거는 저장소 HAL의 `TIM_Encoder_InitTypeDef`, `HAL_TIM_Encoder_Init()`, `HAL_TIM_Encoder_Start()` 구현이다.

## 10. 16비트 카운터를 누적 위치로 읽는 방법

STM32F103C8의 TIM2/TIM3는 16비트다. 다른 STM32 계열의 32비트 TIM2 예제를 그대로 적용해서는 안 된다. 이 칩의 타이머 폭은 [DS5319의 Timers 항목](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)에 명시되어 있다.

ARR=65535이면 CNT는 0~65535 사이에서 순환한다. CPU가 일정 주기마다 현재 값과 직전 값의 차이를 구해 더 큰 누적 변수에 더하는 안을 권장한다.

```c
// 설명용 차분 예시. 미적용. dt 제한·fault 처리·누적 경계 처리는 별도 필요.
uint16_t now = (uint16_t)__HAL_TIM_GET_COUNTER(&htim2);
uint16_t raw_delta = (uint16_t)(now - previous);
int32_t delta = (raw_delta < 32768U)
    ? (int32_t)raw_delta
    : (int32_t)raw_delta - 65536;
previous = now;
// 검증된 delta를 motor1_encoder_count_x4 등의 누적 변수에 반영
```

예: 65534→2이면 +4, 2→65534이면 -4로 복원한다. 매번 CNT를 0으로 초기화하는 방식은 읽기와 리셋 사이 펄스 손실을 만들 수 있으므로 피한다. 시작 시 CNT와 `previous`를 일치시킨 뒤 누적을 시작한다.

**샘플 사이 최대 이동량이 32768 count 미만이어야 방향을 모호함 없이 복원할 수 있다.** 최대 계수율을 `f_count_max`라 하면 `f_count_max × 최대_읽기_간격_s < 32768`을 충분한 여유로 만족시켜야 한다. 정확히 32768은 부호 구분이 불가능하다.

센서 A의 회전당 펄스가 `PPR_A`, 엔코더 축 최대 회전수가 `RPM_max`라면 x4 기준 `f_count_max = 4 × PPR_A × RPM_max / 60`이다. 감속기 출력축 RPM을 사용할 경우 엔코더가 달린 축과 감속비를 먼저 반영해야 한다.

예를 들어 100,000 count/s라는 가정에서는 이론상 읽기 간격이 327.68 ms 미만이어야 한다. 실제 제어 주기는 이 경계보다 훨씬 짧게 잡는다. 1 ms 주기는 검토 출발점일 뿐 최대 속도와 CPU 실행 시간을 확인해야 한다.

PC/ESP32의 100 ms 조회에 누적 갱신을 종속시키지 않는다. STM32 내부 주기 작업에서 갱신하고 I2C는 스냅샷만 가져간다. 주기 작업이 지연되어 허용 간격을 넘으면 잘못된 차분을 정상값으로 쓰지 말고 fault로 처리해야 한다. int64 누적을 선택하면 I2C 인터럽트와 공유할 때 찢어진 읽기를 막는 스냅샷 처리도 필요하다.

## 11. 통신 단위와 기존 코드에 미치는 영향

**현재 공용 프로토콜은 모터2 count를 x1로 정의한다. x4 카운트를 같은 의미인 것처럼 넣으면 안 된다.** 같은 한 바퀴라도 전송 숫자가 대략 4배가 되므로 바이트 길이가 같더라도 의미상 호환성이 달라진다.

향후에는 `protocol/protocol.md`에 계수 배율·부호·회전당 카운트·범위 초과 정책을 먼저 기록하고, x4 원시값을 노출한다면 프로토콜 버전을 올리는 방향을 권장한다. 새 버전 숫자와 패킷 구조는 이 설계안에서 확정하지 않는다.

| 구성요소 / 파일 | 향후 필요한 변경 |
|---|---|
| `protocol/protocol.md` | x1→x4 의미 변경, 단위·버전·호환성 정의 |
| `mobility.ioc` | TIM2/TIM3 Encoder, 리맵, TIM1 CH1/2/3 PWM, 핀·EXTI 변경 |
| `Core/Inc/main.h` | 모터1 PA15/PB3, 모터2 PB4/PB5 라벨·매크로 |
| `Core/Src/main.c` 초기화 | TIM2/TIM3 PWM 초기화를 Encoder 초기화로 전환; TIM1 PWM 채널 추가 |
| `main.c`의 `ApplyCommand()` | 모터1 htim1/CH2, 모터2 htim1/CH1, 모터3 htim1/CH3로 변경; `k`도 세 채널 확인 |
| `main.c`의 카운터 처리 | EXTI 증감 대신 주기 차분·누적·부호·범위 처리 |
| `main.c`의 상태 준비 | 확정 프로토콜에 맞는 스냅샷; 현재 가짜 angle 경로 검토 |
| `stm32f1xx_hal_msp.c` | `HAL_TIM_Encoder_MspInit()` 입력·클록·리맵, PWM PA8/9/10 설정 |
| `stm32f1xx_it.c` 및 헤더 | 엔코더 EXTI3/4 제거, 필요 시 주기 작업 IRQ 추가 |
| ESP32 `.ino` | 새 버전·단위 수신 및 표시 처리 |
| Python | 단순 로그 출력은 유지 가능하나 count 해석·향후 각도 계산은 새 단위 적용 |

모터1의 기존 `carrierAngleTenths = encoderCount % 32000`은 현재도 실제 각도 환산이 아니다. x4로 바꿔도 이 식이 실제 각도가 되지는 않는다. 원시 카운트와 실제 각도 필드를 명확히 구분해야 한다.

기존 숫자 규모 유지 목적으로 x4를 단순히 4로 나누는 호환안도 가능하지만, 기존 A 상승 시점의 x1 카운트와 부분 주기·영점·반전 경계에서 완전히 동일하지 않다. 이를 자동으로 완전 호환이라고 판단하지 않는다.

## 12. 증상

새 오류가 보고된 것은 아니다. 기존 EXTI 계수를 하드웨어 타이머 방식으로 옮길 때의 이점과 전체 핀 자원 충돌을 검토하는 설계 요청이다.

## 13. 재현 절차

1. 현재 `main.c`의 EXTI 콜백, TIM1/2/3 초기화와 `ApplyCommand()`를 읽는다.
2. `.ioc`에서 PA0/PA1 주소, PB6/PB7 I2C, 세 모터 PWM과 방향 핀을 표시한다.
3. ST 데이터시트의 LQFP48 핀 기능과 HAL 리맵 매크로를 대조한다.
4. 엔코더마다 같은 TIM의 CH1/CH2를 배정하고, 그 TIM의 기존 고정 주파수 PWM을 다른 TIM으로 이동시킨다.
5. 최종 표에서 핀 중복과 채널 중복, PWM 주파수 공유 조건을 확인한다.

## 14. 기대 동작

두 모터 엔코더가 CPU의 매 에지 EXTI 처리 없이 독립 누적되고, 세 모터 PWM의 듀티는 각각 제어된다. I2C 통신과 모듈 주소·SWD가 유지되며, 엔코더 값의 단위는 프로토콜과 일치해야 한다.

## 15. 조사 내용과 측정값

현재 저장소의 C·헤더·`.ioc`·HAL 드라이버와 ST 공식 데이터시트를 대조했다. 권장안의 타이머·핀 배치는 이 자료에서 도출한 설계 판단이다. 실제 펄스 속도, CPU 사용률, 신호 전압·파형, 회전당 count는 측정하지 않았다.

### 근거 자료

- [저장소 ST HAL TIM 헤더](../../stm32/mobility/Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_tim.h): EncoderMode, 입력 설정 구조체, API.

## 16. 원인

재배치가 필요한 이유는 일반 GPIO의 자유로운 선택과 달리 Encoder Mode에는 CH1/CH2 핀 제약과 타이머 공통 CNT 제약이 있기 때문이다. 현재 핀쌍은 해당 조건을 만족하지 않으며, 사용하려는 TIM2/TIM3에 기존 PWM이 배정되어 있다.

## 17. 해결 또는 임시 조치

TIM2=모터1 엔코더, TIM3=모터2 엔코더, TIM1 CH1/2/3=세 모터 PWM이라는 검토안을 제시했다. 실제 변경은 수행하지 않았다.

## 18. 검증 결과

- 소스의 기존 자원과 제안 핀·채널 중복을 검토했다.
- 사용한 리맵 조합이 저장소 HAL에 존재하며 제안 핀이 LQFP48에 있음을 확인했다.
- 문서의 로컬 링크와 변경 범위를 확인했다.
- CubeMX에서 실제 설정 적용·코드 재생성·컴파일·플래시·실기 검증은 **미수행**이다. 이 문서는 “컴파일 확인” 또는 “실기 검증 완료” 결과물이 아니다.

## 19. 남은 위험과 후속 작업

구현 전 센서 PPR·최대 축 RPM·출력 전압·출력 방식, 보드 헤더 접근성, 세 모터의 동일 PWM 주파수 사용 가능 여부를 확정한다. 입력 필터·내부 갱신 주기는 그 결과로 결정한다.

향후 적용 시 먼저 공용 규격을 정하고, 별도 변경으로 CubeMX·코드를 수정한 후 컴파일한다. 모터 전원을 끈 상태에서 배선 전환과 SWD·I2C·주소를 확인하고, 축 수동 회전으로 부호·한 바퀴 count·양방향 순환 경계를 검증한다. 이어 모터 전원을 넣기 전 PWM 세 채널의 주파수·듀티·정지 출력을 측정한다.

실기 확대는 저속·저출력, 무부하, 단일 모듈, 전체 모듈 순서로 진행한다. 현재 ±70 출력 명령을 그대로 초기 저출력 시험으로 사용하지 않는다. 정지 판정·센서 이상·시간 초과·통신 두절 인터록은 타이머 전환과 별도로 검증하고, 모터1 정지 전 정렬 금지, 모터2 정지 전 클러치 동작 금지, 모터3 동작 중 모터1·2 정지 조건을 유지한다.
