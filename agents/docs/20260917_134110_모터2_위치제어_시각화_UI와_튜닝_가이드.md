# 20260917_134110 모터2 위치제어 시각화 UI와 튜닝 가이드

## 1. 목적

현재 모터2는 목표까지 고정 70% PWM으로 이동하고 목표 허용오차 진입 또는 목표 통과 시
출력을 0으로 만드는 방식이다. 이 문서는 실제 count, 목표 count와 PWM을 시간축으로
확인하여 오차가 관성 오버슈트인지, 환산비 오차인지, 백래시인지 구분하는 절차를 설명한다.

PC UI 파일은 다음과 같다.

```text
pc/motor_control_tuning_ui.py
```

외부 그래프 패키지는 사용하지 않는다. Python이 localhost 서버를 열고 기본 브라우저의
HTML Canvas로 그래프를 표시하며 기존 pyserial만 사용한다. 현재 PC의 Python 설치에서
Tcl/Tk 런타임이 빠져 있어 Tkinter 창을 만들 수 없었기 때문에 브라우저 UI로 구성했다.

## 2. UI를 위한 프로토콜 버전 7

STM32 상태 응답을 11바이트에서 18바이트로 확장했다.

| 데이터 | 목적 |
|---|---|
| 실제 `motor2_count` | 시간에 따른 실제 위치 확인 |
| `target_count` | 실제 위치와 목표 위치 직접 비교 |
| `motor2_pwm` | PWM이 70%에서 0으로 바뀌는 시점 확인 |
| `target_step` | 기준점에서 몇 번째 20도 홈인지 확인 |
| state, error, clutch, 출력각, motor3 PWM | 기존 상태와 안전 진단 유지 |

ESP32는 UI가 USB로 `v`를 보낸 동안에만 `TELEM_M37`을 100ms마다 출력한다. UI 종료 시
`V`와 정지 명령을 보내므로 평소 터미널의 저빈도 로그 정책은 유지된다.

STM32 내부 위치 제어는 약 10ms 주기이고 UI 표본은 100ms 주기다. 따라서 아주 짧은 순간의
최대 count를 모두 포착하지 못할 수 있지만, 목표 통과 방향, PWM 차단 전후의 count 변화와
300ms 뒤 최종 정지 위치는 확인할 수 있다. 더 높은 시간 해상도가 필요하면 I2C 안정성을
먼저 확인한 뒤 별도 고속 버퍼 또는 STM32 직접 텔레메트리를 설계해야 한다.

## 3. 실행 전 준비

패킷 길이와 버전이 바뀌었으므로 다음 세 구성요소를 같은 작업 트리 기준으로 사용한다.

1. STM32 version 7 코드를 Build하고 STM32에 Flash한다.
2. ESP32 version 7 스케치를 Build하고 ESP32에 업로드한다.
3. 기존 키보드 프로그램과 Arduino Serial Monitor를 종료하여 COM7을 비운다.
4. 저장소 루트에서 UI를 실행한다.

```powershell
python .\pc\motor_control_tuning_ui.py --port COM7
```

브라우저가 `http://127.0.0.1:8765/`로 자동으로 열린다. 포트가 다르면 UI 상단에서
선택하거나 `--port` 값을 바꾼다. 자동으로 열리지 않으면 터미널에 표시된 주소를 브라우저에
직접 입력한다. 종료는 실행 터미널에서 `Ctrl+C`를 누른다.

## 4. UI 구성

### 실시간 상태

- state와 한글 상태명
- error 번호와 CE 오류명
- 클러치 계산 모드
- 실제 count와 목표 count
- 위치 오차 `목표 - 실제`
- 모터2·모터3 PWM
- 선택 출력축 각도와 목표 홈 번호

### 버튼 제어

| 버튼 | 동작 |
|---|---|
| 전체 정지 | 모터1·2·3 정지 명령 `k` |
| 클러치 A 방향 조그 | 정지 후 350ms 대기하고 모터3 `u` |
| 클러치 B 방향 조그 | 정지 후 350ms 대기하고 모터3 `o` |
| A 계산모드 선택 | 정지 후 350ms 대기하고 15:1 모드 `a` |
| B 계산모드 선택 | 정지 후 350ms 대기하고 12:1 모드 `b` |
| 현재 홈을 0도로 저장 | 기준 설정 `z` |
| 출력축 -20도 | 목표 홈 한 칸 감소 `n` |
| 저장한 0도로 복귀 | 목표 홈 0 `r` |
| 출력축 +20도 | 목표 홈 한 칸 증가 `p` |

상태를 받기 전에는 이동 버튼이 비활성이다. 모터2 이동 중에는 새 이동 명령을 막고,
클러치 조그 중에는 모터2 버튼을 막는다. 최종 안전 판정은 계속 STM32에서 수행한다.

정상적인 최초 화면에서 `state=0`, 계산 모드가 `미선택`이면 ±20도와 홈 저장 버튼이
비활성화된다. 이때 오류가 발생한 것은 아니다. 버튼 영역의 안내에 따라 실제 클러치 상태와
일치하는 A/B 계산모드를 먼저 선택하고, 실제 홈을 맞춘 뒤 현재 홈을 0도로 저장한다.
`state=1`이 되면 ±20도와 0도 복귀 버튼이 활성화된다.

상단에 `UI rev.2`가 보여야 버튼 이름 충돌 수정본이 실행 중인 것이다. 버튼을 누르면 버튼
영역 아래에 `최근 버튼: a (서버 접수 완료)`처럼 표시되며, 통신 로그에는 정지 대기와 실제
명령 기록이 추가된다. `UI rev.2`가 없으면 실행 중인 Python UI를 종료하고 다시 시작한 뒤
브라우저에서 `Ctrl+F5`로 새로고침한다.

통신 로그는 새 줄이 들어올 때마다 자동으로 맨 아래로 이동하여 항상 최신 기록을 표시한다.

### 그래프

- 하늘색: 실제 motor2 count
- 주황색: target count
- 빨강: motor2 PWM
- 표시 범위: 최근 20초
- CSV 저장: 화면에 수집된 전체 표본을 UTF-8 CSV로 저장

CSV에는 시간, state, 모드, 출력각, 실제·목표 count, 위치 오차, PWM과 목표 홈을 저장한다.

### 소스 튜닝값

UI 오른쪽은 `carrier_test.h`의 실제 `#define` 값을 읽어 표시한다. IDE에서 직접 값을
바꿨다면 `소스 다시 읽기`를 눌러 현재 파일값을 확인할 수 있다.

튜닝 영역은 한 화면에 들어오도록 작은 글자와 좁은 숫자 입력 칸으로 표시한다. 항목 이름에
마우스를 올리면 내부 `#define` 이름을 확인할 수 있다. 화면 폭이 좁으면 오른쪽 영역이
그래프 아래로 자동 이동한다.

`carrier_test.h에 저장`은 입력값 범위를 검사한 뒤 소스의 숫자만 바꾼다. 실행 중인
STM32에는 즉시 적용되지 않는다. 반드시 CubeIDE에서 다시 Build/Flash해야 한다.

다음 값은 특히 주의해서 변경한다.

- PWM은 0~100 범위
- 관찰 모드는 0 또는 1
- `MOTOR2_PWM_TO_COUNT_SIGN`은 -1 또는 1
- 통신 timeout을 ESP32 100ms polling에 지나치게 가깝게 낮추지 않음
- 최대 홈 수를 늘리면 최대 count 범위도 함께 검토

## 5. 현재 오버슈트 측정 순서

제어 알고리즘을 바꾸기 전에 고정 70%의 기준 데이터를 수집한다.

1. UI를 연결하고 `state`, `error`, 실제 count가 갱신되는지 확인한다.
2. 전체 정지를 누른다.
3. 실제 클러치를 A에 체결하고 A 계산모드를 선택한다.
4. 캐리어 실제 홈에서 현재 홈을 0도로 저장한다.
5. 그래프를 지운다.
6. `+20°`를 한 번만 누른다.
7. state 2에서 3이 될 때까지 추가 버튼을 누르지 않는다.
8. 목표 count, PWM이 0이 된 count, 최종 정지 count를 기록한다.
9. 같은 방향으로 여러 칸 반복하고 CSV를 저장한다.
10. `-20°`와 0도 복귀도 같은 방식으로 측정한다.
11. 클러치 B에서도 새 기준점을 잡고 동일하게 반복한다.

오버슈트 count는 이동 방향을 고려하여 보거나 우선 절댓값으로 비교한다.

```text
최종 위치 오차 = 최종 motor2_count - target_count
```

## 6. 그래프 해석과 다음 수정

| 관찰 결과 | 가능성이 큰 원인 | 다음 조치 |
|---|---|---|
| 매 이동마다 같은 방향으로 비슷한 count 초과 | 고정 70%와 관성 정지 | 목표 전 PWM 감속 구간 추가 |
| 이동 칸 수가 커질수록 각도 오차가 비례 증가 | count/회전 또는 감속비 환산 오류 | 실제 1회전 count와 20도 환산값 재측정 |
| 정방향과 역방향 오차 부호·크기가 다름 | 기어 백래시 | 항상 같은 방향에서 홈에 접근하거나 백래시 보상 검토 |
| 목표 통과 후 count가 오랫동안 계속 증가 | 관성·제동 부족 | 감속 시작 거리를 늘리고 PWM을 낮춤 |
| 같은 ±20도 버튼을 다시 눌렀는데 반대로 이동하려 함 | 직전 오버슈트가 다음 홈 목표까지 통과 | 실제·목표 count 확인, 기준 재설정, 감속 제어 적용 |
| PWM이 켜졌지만 count가 계단식 또는 누락 | 엔코더·인터럽트 문제 | 신호와 누락 여부를 우선 확인 |
| motor2 count는 맞지만 실제 홈이 어긋남 | 모터 엔코더 이후 기계 유격·미끄러짐 | 출력축 기준 센서 또는 홈 센서 검토 |

첫 제어 개선은 PID 전체보다 단계식 감속을 권장한다.

```text
목표에서 멀 때       → 70%
감속 구간 진입        → 중간 PWM
목표 바로 앞          → 최소 이동 PWM
허용오차 또는 목표 통과 → 0%
```

손 튜닝 순서는 다음과 같다.

1. 70% 기준 CSV에서 PWM 0 이후 추가로 움직인 count를 구한다.
2. 그 count보다 여유 있게 먼 지점에서 첫 감속을 시작한다.
3. 중간 PWM은 모터가 부하 상태에서 계속 움직일 수 있는 값보다 높게 잡는다.
4. 오버슈트가 크면 감속 시작 거리를 늘리거나 근접 PWM을 낮춘다.
5. 목표 전에 멈추면 근접 PWM을 올리거나 감속 시작 거리를 줄인다.
6. 최종 오차가 방향별로 다르면 PWM보다 백래시를 먼저 의심한다.
7. 단계식 제어 데이터가 안정되면 `PWM = Kp × 위치오차 - Kd × 속도` 형태의 PD 제어를 검토한다.
8. 적분 I는 백래시·정지마찰에서 wind-up을 만들 수 있으므로 처음에는 사용하지 않는다.

현재 UI는 측정과 기존 상수 편집까지 제공하며 단계식/PID 계수는 아직 펌웨어에 구현하지
않았다. 현재 그래프로 기준 데이터를 확보한 뒤 별도 제어 변경으로 추가한다.

안전 보강된 STM32 코드는 `p/n`의 다음 홈이 이미 현재 위치 반대쪽에 놓인 경우 역방향으로
보정하지 않고 `CE_DIRECTION=5`로 정지한다. 이 경우 전체 정지 후 실제 홈을 확인하고 계산
모드와 0도 기준을 다시 설정한다.

## 7. 조립 상태별 시험 순서

최종 튜닝값은 실제 관성, 마찰, 클러치 압력과 백래시가 모두 반영되는 완전조립 상태에서
확정해야 한다. 그러나 첫 검증부터 완전조립으로 시작하면 오차 원인과 기계 걸림을 구분하기
어렵고 위험도 커진다.

### 1단계: 무부하 단일 모듈

- 바퀴 하중 없이 모터2 방향, 엔코더 부호와 UI 그래프 확인
- 정지 버튼, timeout, stall과 통신 단절 정지 확인
- 낮은 횟수의 ±20도 이동으로 텔레메트리 정상성 확인

### 2단계: 유성기어와 클러치가 결합된 단일 모듈

- 실제 링기어·캐리어 관성, 마찰과 백래시 포함
- 클러치 A/B 각각의 목표·최종 count 오차 측정
- 홈 체결 가능 여부와 방향 전환 오차 측정
- 단계식 감속 또는 PD 값의 주된 튜닝은 이 단계에서 수행

### 3단계: 완전조립, 무부하 또는 차체를 들어 올린 상태

- 전체 조립 공차와 바퀴 관성을 포함한 최종값 확인
- 즉시 전원 차단 준비 후 한 모듈씩 시험
- 클러치 전환 중 다른 축이 끌려가는지 확인

### 4단계: 지면 부하

- 가장 낮은 속도와 짧은 횟수부터 시작
- 하중에 따른 정지 오차, 전류, 발열과 반복성을 확인
- 단일 모듈 검증 뒤 전체 모듈로 확대

따라서 “최종 튜닝은 완전조립 상태에서 해야 한다”는 판단은 맞지만, UI와 제어 변경의 최초
검증은 단계적으로 진행해야 한다.

## 8. 안전 및 한계

- 모터3에는 위치 센서가 없어 클러치 체결 완료를 자동으로 알 수 없다.
- 현재 100ms UI 표본은 최종 오버슈트 측정에는 유용하지만 10ms 내부 궤적 전체는 아니다.
- UI가 끊겨도 STM32 timeout, stall, 방향, 범위와 클러치 인터록은 계속 동작한다.
- UI에서 상수를 저장한 직후 실행 중인 펌웨어와 화면의 소스값은 서로 다를 수 있다.
- 소스 변경 후 Build/Flash 전에는 실제 보드가 이전 값을 사용한다.
- 완전조립 시험에서는 홈 미정렬 상태로 클러치 모터를 반복 구동하지 않는다.

## 9. 문제 해결

### UI에 데이터가 표시되지 않음

- Arduino Serial Monitor와 기존 키보드 프로그램이 COM 포트를 사용 중인지 확인한다.
- STM32와 ESP32가 모두 wire version 7인지 확인한다.
- 로그에 `bytesReceived=11`이 보이면 STM32가 이전 version 6이다.
- 로그에 `bytesReceived=18`인데 ok=false면 version 값과 I2C write error를 확인한다.

### UI 저장값이 모터에 적용되지 않음

- 저장은 `carrier_test.h`만 변경한다.
- CubeIDE에서 Clean/Build 후 STM32에 Flash한다.
- 다시 UI에서 소스값을 읽고 실기 로그의 PWM·시간 동작을 확인한다.

### 그래프가 너무 성김

- 기본 I2C 안정성을 위해 100ms를 유지한 상태다.
- 먼저 최종 정지 오차와 반복성을 판단한다.
