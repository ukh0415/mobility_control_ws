# 모터1·모터2 엔코더 읽기 비교와 코드 안내

## 1. 결론: 읽는 원리는 같고, 값 처리와 설정 관리 방식은 다르다

**현재 두 엔코더 모두 A상 상승 에지에서 외부 인터럽트(EXTI)를 발생시키고, B상의 상태를 읽어 카운트를 +1 또는 -1 하는 x1 방식이다.** 타이머의 Encoder Mode로 하드웨어 계수하는 방식은 아니다.

| 비교 항목 | 모터1: 기존 바퀴 엔코더 | 모터2: 추가 엔코더 |
|---|---|---|
| A상 / ENA | PA4 | PB3 |
| B상 / ENB | PA5 | PB5 |
| A상 입력 | 상승 에지 인터럽트 | 상승 에지 인터럽트 |
| B상 입력 | 일반 GPIO 입력 | 일반 GPIO 입력 |
| 내부 풀업·풀다운 | 둘 다 사용 안 함 | 둘 다 사용 안 함 |
| 인터럽트 | EXTI4_IRQn | EXTI3_IRQn |
| 우선순위 설정 | (5, 0) | (5, 0) |
| B=Low일 때 | +1 | +1 |
| B=High일 때 | -1 | -1 |
| 누적 변수 | `volatile int32_t encoderCount` | `volatile int32_t motor2_encoder_count` |
| 부팅 초기값 | 0 | 0 |
| int32 범위 초과 처리 | 별도 처리 없음 | 최대·최솟값 사이 명시적 순환 |
| 외부로 보내는 값 | `encoderCount % 32000`을 int16 필드로 전송 | 원시 int32 카운트를 전송 |
| USB 로그 표시 | `angle=`: 전송값을 10으로 나누어 표시 | `motor2_count=`: 카운트 그대로 표시 |
| 실제 각도·RPM 환산 | 미구현 | 미구현 |
| 엔코더 기반 위치·속도 제어 | 미구현 | 미구현 |

여기서 모터1은 기존 문서의 바퀴 엔코더 PA4/PA5를 뜻한다. 코드에서는 `motor1_encoder_count`라는 이름 대신 `encoderCount`와 `WHEEL_ENC_*`라는 이름을 사용한다. 실제 배선이 이 소스의 배정과 같은지는 이번 작업에서 측정하지 않았다.

## 4. 핀 배정: 엔코더 입력과 모터 구동 출력을 구분하기

### 엔코더 입력 핀의 이름

`main.h`에 다음과 같이 정의되어 있다.

```c
// 기존 모터1: Private defines 영역, 62행부터
#define WHEEL_ENC_A_Pin GPIO_PIN_4
#define WHEEL_ENC_A_GPIO_Port GPIOA
#define WHEEL_ENC_A_EXTI_IRQn EXTI4_IRQn
#define WHEEL_ENC_B_Pin GPIO_PIN_5
#define WHEEL_ENC_B_GPIO_Port GPIOA

// 모터2: USER CODE BEGIN Private defines 영역, 69행부터
#define MOTOR2_ENC_A_Pin GPIO_PIN_3
#define MOTOR2_ENC_A_GPIO_Port GPIOB
#define MOTOR2_ENC_B_Pin GPIO_PIN_5
#define MOTOR2_ENC_B_GPIO_Port GPIOB
```

`GPIO_PIN_5`는 핀 번호를 나타내는 비트 마스크다. 포트와 함께 읽어야 하므로 `GPIOA + GPIO_PIN_5`는 PA5, `GPIOB + GPIO_PIN_5`는 PB5이다. 두 B상은 번호만 5로 같고 서로 다른 물리 입력이다. B상에는 인터럽트를 걸지 않으므로 두 핀이 EXTI5를 공유하는 문제도 현재 구성에는 없다.

모터2에는 `MOTOR2_ENC_A_EXTI_IRQn` 매크로가 없다. 초기화 코드가 `EXTI3_IRQn`을 직접 사용한다.

### 관련 모터 구동 핀

| 용도 | 모터1 | 모터2 |
|---|---|---|
| 엔코더 A/B 입력 | PA4 / PA5 | PB3 / PB5 |
| PWM 출력 | PA6, TIM3_CH1 | PA8, TIM1_CH1 |
| 방향 출력 두 개 | PA7 / PB0 | PB1 / PB10 |
| PWM 핸들 변수 | `htim3` | `htim1` |
| 현재 구동 명령 | `i` / `,` | `j` / `l` |

근거는 `main.c`의 `ApplyCommand()`와 `stm32f1xx_hal_msp.c`의 `HAL_TIM_MspPostInit()`이다. **모터 번호와 타이머 번호는 일치하지 않는다.** 모터1이 TIM3, 모터2가 TIM1을 PWM에 사용한다. ENA/ENB는 이 문서에서 엔코더 신호이며 PWM이나 방향 제어선이 아니다.

## 5. GPIO와 인터럽트 세부 설정

### 공통 설정 의미

| 설정 | 현재 값 | 쉬운 설명 |
|---|---|---|
| A상 모드 | `GPIO_MODE_IT_RISING` | A가 Low에서 High로 바뀔 때 CPU에 처리 요청 |
| B상 모드 | `GPIO_MODE_INPUT` | 필요할 때 현재 Low/High를 읽음 |
| Pull | `GPIO_NOPULL` | MCU 내부 풀업·풀다운 저항을 사용하지 않음 |
| NVIC | `HAL_NVIC_EnableIRQ(...)` | 해당 인터럽트를 CPU가 처리하도록 허용 |
| 우선순위 | `HAL_NVIC_SetPriority(..., 5, 0)` | 두 엔코더에 같은 우선순위를 부여 |
| 필터·디바운스 | 별도 구현 없음 | 코드에 펄스 폭 검사나 노이즈 제거 로직 없음 |

`GPIO_NOPULL`은 외부 회로에도 풀업이 없다는 뜻은 아니다. 외부 풀업 유무, 센서 출력 방식·전압은 별도 확인이 필요하다. 입력용 코드에는 엔코더 샘플링 주파수나 `ICxFilter` 같은 타이머 입력 필터 설정이 없다.

모터2는 B부터 설정한 다음 A를 설정한다. A 설정 직전에 `Pull` 대입이 다시 없지만 **같은 `GPIO_InitStruct`에 남아 있는 `GPIO_NOPULL`을 그대로 사용하므로 A도 NOPULL이다.** 모터1은 A부터 설정한다는 순서 차이는 있으나 최종 입력 모드는 같다.

두 포트의 클록은 같은 함수 앞부분의 `__HAL_RCC_GPIOA_CLK_ENABLE()`과 `__HAL_RCC_GPIOB_CLK_ENABLE()`로 켠다.

### PB3의 JTAG 설정

`stm32f1xx_hal_msp.c:79`에 기존부터 다음 설정이 있다.

```c
__HAL_AFIO_REMAP_SWJ_NOJTAG();
```

이 설정은 JTAG 기능을 해제해 PB3를 GPIO로 사용할 수 있게 하며 SWD 디버깅은 유지한다. `HAL_Init()` 과정의 `HAL_MspInit()`에서 적용되고, 이후 `MX_GPIO_Init()`가 PB3 입력을 설정한다. PA4/PA5에는 이 PB3 관련 해제 절차가 필요하지 않다.

## 6. 실제로 카운트를 읽는 순서

```text
모터1 A(PA4) 상승
  → EXTI4_IRQHandler()                    [stm32f1xx_it.c:204]
  → HAL_GPIO_EXTI_IRQHandler(WHEEL_ENC_A_Pin)
  → HAL_GPIO_EXTI_Callback(GPIO_PIN_4)     [main.c:189]
  → PA5를 읽음 → encoderCount 증감

모터2 A(PB3) 상승
  → EXTI3_IRQHandler()                    [stm32f1xx_it.c:244]
  → HAL_GPIO_EXTI_IRQHandler(MOTOR2_ENC_A_Pin)
  → HAL_GPIO_EXTI_Callback(GPIO_PIN_3)     [main.c:189]
  → PB5를 읽음 → motor2_encoder_count 증감
```

저장소 HAL 드라이버의 `stm32f1xx_hal_gpio.c:546`에 있는 `HAL_GPIO_EXTI_IRQHandler()`가 pending 상태를 확인하고 지운 뒤 공통 콜백을 호출한다. 사용자 콜백은 전달받은 핀 마스크로 두 엔코더를 구분한다. 콜백 인자 자체에는 GPIOA/GPIOB 포트 정보가 없고, 해당 EXTI 라인의 포트 연결은 GPIO 초기화에서 정해진다.

### 왜 x1인가?

현재는 A의 상승 에지 하나만 센다. A 하강이나 B 상승·하강에서는 카운트를 바꾸지 않는다. 따라서 A 신호 한 주기마다 한 번 계산한다.

| 사건 | 두 모터의 처리 |
|---|---|
| A 상승, 콜백에서 읽은 B=Low | 카운트 +1 |
| A 상승, 콜백에서 읽은 B=High | 카운트 -1 |
| A 하강만 발생 | 카운트 변화 없음 |
| B만 변함 | 카운트 변화 없음 |

예를 들어 A 상승이 100회 발생하고 각 처리 시 B가 모두 Low라면 0에서 +100이 된다. 이는 설명용 예이며 실제 측정값은 아니다. x4라면 이상적인 A/B 한 주기의 네 에지를 세지만, 현재 두 모터는 그 방식으로 설정되어 있지 않다.

엄밀히 말해 B는 A 상승 순간에 하드웨어로 함께 저장되는 것이 아니라 **인터럽트 콜백이 실행될 때 소프트웨어가 읽는다.** 처리 지연이 크면 B가 이미 바뀌어 방향을 잘못 판단하거나 여러 A 에지를 놓칠 가능성이 두 모터 모두 있다.

Low=+1 규칙이 같아도 실제 축의 시계·반시계 방향이 같다는 보장은 없다. A/B 배선, 센서 부착 방향과 기구 배치에 따라 달라지므로 실기 확인이 필요하다.

### 모터1: 단순 증감

`main.c:200`부터 다음 분기가 있다.

```c
if (GPIO_Pin == GPIO_PIN_4)
{

  {
    encoderCount++;
  }
  else
```

초기화에는 `WHEEL_ENC_*` 매크로를 사용하지만 이 콜백에는 PA4/PA5를 직접 적었다. 따라서 향후 모터1 핀을 바꾸면 `main.h`만 바꾸지 말고 이 부분도 함께 확인해야 한다.

### 모터2: 경계 확인 후 증감

`main.c:191`부터 다음 분기가 있다.

```c
if (GPIO_Pin == MOTOR2_ENC_A_Pin)
{
  if (HAL_GPIO_ReadPin(MOTOR2_ENC_B_GPIO_Port, MOTOR2_ENC_B_Pin) == GPIO_PIN_RESET) {
    motor2_encoder_count = (motor2_encoder_count == INT32_MAX) ? INT32_MIN : motor2_encoder_count + 1;
  } else {
    motor2_encoder_count = (motor2_encoder_count == INT32_MIN) ? INT32_MAX : motor2_encoder_count - 1;
  }
}
```

모터2는 콜백에서도 핀 매크로를 사용한다. `int32_t` 범위는 -2,147,483,648부터 +2,147,483,647까지이며 모터2는 최대에서 +1이면 최소, 최소에서 -1이면 최대로 명시적으로 이동한다.

모터1에는 이 처리가 없어 경계를 넘는 signed 정수 연산의 동작을 C 코드 차원에서 보장하지 않는다. 아래의 `% 32000`은 전송용 값을 만드는 처리일 뿐, `encoderCount` 자체를 줄이거나 이 오버플로를 방지하지 않는다.

두 카운터는 부팅 시 0이고, 현재 코드에 운전 중 영점 재설정이나 원점 센서 처리, 비휘발성 저장은 없다. 정지 명령 `k`도 카운터를 0으로 만들지 않는다.

## 8. main 루프와 타이머는 어떤 역할인가?

`main()`은 `HAL_Init()` → `SystemClock_Config()` → `MX_GPIO_Init()` 순서로 초기화한다. 엔코더 입력은 GPIO와 NVIC 설정으로 활성화되며 별도의 `HAL_TIM_Encoder_Start()` 호출은 없다. 엔코더 계수는 main 루프가 입력을 반복 조회하는 방식이 아니라 인터럽트에서 수행된다.

현재 main 루프의 관련 코드는 모터1 값 가공뿐이다.

```c
carrierAngleTenths = (int16_t)(encoderCount % 32000);
```

모터2 카운터는 여기서 읽거나 환산하지 않는다. `PrepareStatusBuffer()`가 I2C 읽기 요청 시 직접 읽는다. 모터1의 상태 필드는 루프에서 마지막으로 갱신한 값이고, 모터2는 패킷 준비 시점의 스냅샷이므로 두 값이 정확히 같은 시점의 측정값이라고 볼 수도 없다.

### 타이머 세부 설정은 엔코더용이 아니라 PWM용이다

| 항목 | 모터1 PWM | 모터2 PWM |
|---|---|---|
| 함수 | `MX_TIM3_Init()` | `MX_TIM1_Init()` |
| 핸들·채널 | `htim3`, `TIM_CHANNEL_1` | `htim1`, `TIM_CHANNEL_1` |
| Prescaler | 71 | 71 |
| Period | 999 | 999 |
| CounterMode | `TIM_COUNTERMODE_UP` | `TIM_COUNTERMODE_UP` |
| ClockDivision | `TIM_CLOCKDIVISION_DIV1` | `TIM_CLOCKDIVISION_DIV1` |
| AutoReloadPreload | DISABLE | DISABLE |
| 출력 모드 | `TIM_OCMODE_PWM1` | `TIM_OCMODE_PWM1` |
| 초기 Pulse | 0 | 0 |
| 출력 극성 / FastMode | HIGH / DISABLE | HIGH / DISABLE |
| 시작 함수 | `HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1)` | `HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_1)` |

`.ioc`의 타이머 클록 72 MHz 기준 PWM 주파수는 `72,000,000 / (71 + 1) / (999 + 1) = 1,000 Hz`다. 이는 설정으로 계산한 값이며 오실로스코프로 측정한 값은 아니다. 이 1 kHz나 Period=999는 엔코더 계수 속도·분해능·최댓값과 무관하다.

`SetMotor()`는 명령의 출력 비율을 PWM 비교값에 반영하며 엔코더 피드백은 읽지 않는다. 현재 `i/,/j/l` 명령은 ±70을 전달하므로 저출력 엔코더 검증용 명령으로 그대로 사용해서는 안 된다. 엔코더 진단 계수가 추가되었다고 자동으로 위치·속도 제어나 정지 인터록이 완성된 것은 아니다.

## 9. CubeMX 설정과 수동 코드 관리의 차이

| 항목 | 모터1 | 모터2 |
|---|---|---|
| `.ioc` A상 | `PA4.Signal=GPXTI4` | `PB3.Signal=GPXTI3` |
| `.ioc` B상 | `PA5.Signal=GPIO_Input` | `PB5.Signal=GPIO_Input` |
| GPIO 라벨 | `WHEEL_ENC_A`, `WHEEL_ENC_B` | PB3/PB5에 라벨 설정 없음; 매크로는 수동 정의 |
| EXTI 연결 | `SH.GPXTI4.0=GPIO_EXTI4` | `SH.GPXTI3.0=GPIO_EXTI3` |
| `.ioc` NVIC | `NVIC.EXTI4_IRQn` 활성 설정 있음 | `NVIC.EXTI3_IRQn` 항목 없음 |
| 실행 코드의 NVIC 활성화 | GPIO 생성 영역 | GPIO USER CODE 영역 |
| IRQ 핸들러 | 생성된 EXTI4 함수 | 파일 끝 USER CODE BEGIN 1의 EXTI3 함수 |

모터2의 `.ioc` NVIC 항목이 없다고 실행 코드의 EXTI3가 비활성인 것은 아니다. 현재는 USER CODE에서 직접 활성화한다. `.ioc`는 CubeMX 재생성의 입력 자료이고 실제 실행 동작은 빌드한 C 소스가 결정한다.

현재 `ProjectManager.KeepUserCode=true`다. CubeMX에서 재생성할 때 USER CODE 보존, PB3/PB5 최종 초기화, 핸들러 중복을 확인해야 한다. 특히 EXTI3 NVIC 코드 생성을 새로 켜면 기존 수동 `EXTI3_IRQHandler()`와 중복될 수 있다. 생성 영역과 USER CODE 양쪽에서 PB3/PB5를 초기화하게 되는지도 확인한다.

## 10. PC에서 보이는 값은 왜 서로 다른가?

### STM32 → ESP32 패킷

`PrepareStatusBuffer()`가 다음 8바이트를 만든다. 공용 문서 버전은 `0.2.0-draft`, 패킷 안 진단 버전 숫자는 `2`이다.

| 바이트 | 내용 | 엔코더와의 관계 |
|---|---|---|
| 0 | `currentMode` | 기존 상태 |
| 1–2 | `carrierAngleTenths`, int16 little-endian | 모터1 `encoderCount % 32000` |
| 3 | 2 | 진단 패킷 버전 |
| 4–7 | `motor2_encoder_count`, int32 little-endian | 모터2 원시 누적값 |

모터2는 먼저 `uint32_t motor2_snapshot = (uint32_t)motor2_encoder_count;`로 한 번 읽은 뒤 8비트씩 잘라 담는다. 따라서 네 바이트를 만들 때 서로 다른 시점의 카운트를 반복해서 읽지 않는다. ESP32는 `rawCount`로 조립한 뒤 부호 있는 `out.motor2_encoder_count`로 복원한다.

### 모터1의 angle은 실제 각도가 아니다

```text
PA4/PA5 → encoderCount
        → main 루프: encoderCount % 32000
        → carrierAngleTenths → I2C 바이트 1–2
        → ESP32 legs[i].angle_tenths
        → / 10.0 → USB angle= 및 TCP STATUS
```

예를 들어 모터1 카운트가 123이면 `angle=12.3`으로 보이지만 **이것만으로 12.3도를 회전했다고 해석하면 안 된다.** 엔코더 분해능·감속비를 이용한 변환이 없다. 카운트가 32,000이면 전송값이 0으로 돌아가며 음수 카운트의 나머지는 음수가 될 수 있다.

`carrierAngleTenths`라는 이름도 모터2의 캐리어 각도를 읽는다는 뜻으로 오해하기 쉽다. 현재 대입 원천은 명확히 모터1의 `encoderCount`다. ESP32의 기존 주석에는 0.1도/실제각도라는 표현이 남아 있지만 현재 소스와 공용 프로토콜의 주의사항을 기준으로 해석해야 한다.

### 모터2는 원시 카운트로 표시한다

```text
PB3/PB5 → motor2_encoder_count
        → PrepareStatusBuffer() → I2C 바이트 4–7
        → ESP32 legs[i].motor2_encoder_count
        → USB motor2_count=123
        → Python status_receiver() → 콘솔
```

모터2 카운트가 123이면 그대로 `motor2_count=123`이다. 같은 숫자로 비교하려면 모터1도 디버거에서 `encoderCount` 원시값을 봐야 한다. 현재 USB의 `angle`과 `motor2_count`를 그대로 비교하면 단위와 가공 방식이 달라 혼동한다.

ESP32는 8바이트 수신과 버전 2를 확인한 경우에만 정상 상태로 표시한다. 현재 `ACTIVE_LEG_COUNT=1`, `POLL_INTERVAL_MS=100`으로 0x10 모듈을 약 100 ms 간격으로 조회하도록 구성되어 있다. 이것은 통신 조회 주기이며 STM32 엔코더를 100 ms마다 한 번 세는 뜻은 아니다.

`sendStatusToClient()`의 TCP STATUS에는 모터2 카운트가 들어가지 않는다. `printStatusToSerial()`의 USB 로그에만 추가된다. Python은 `readline()`으로 받은 줄을 그대로 출력하며 별도 카운트 저장·각도 환산을 하지 않는다.

## 11. 증상·재현 절차·기대 동작

### 증상

이번 요청은 “모터2를 추가한 뒤 모터1과 동일하게 읽는가?”에 대한 비교다. 새 하드웨어 고장이나 계수 오류가 관측되었다는 전제는 없다.

### 재현 절차: 소스에서 확인하기

1. `main.h`에서 두 엔코더의 핀 매크로를 확인한다.
2. `MX_GPIO_Init()`에서 A=IT_RISING, B=INPUT, NOPULL과 NVIC를 비교한다.
3. `stm32f1xx_it.c`의 EXTI4/EXTI3가 공통 HAL 처리 함수를 호출하는지 확인한다.
4. `HAL_GPIO_EXTI_Callback()`에서 B상 판독과 카운터 증감을 비교한다.
5. `encoderCount`와 `motor2_encoder_count`의 참조를 검색해 main 루프와 패킷으로 이어지는 경로를 확인한다.
6. ESP32의 `printStatusToSerial()`과 `sendStatusToClient()`에서 표시 차이를 확인한다.

### 기대 동작

정상 A/B 신호가 처리 가능한 속도로 입력되면 해당 엔코더 카운터만 독립적으로 증감한다. 모터 정지 명령 상태에서도 외부에서 축이 움직여 신호가 들어오면 카운트는 바뀐다. 기계적 정·역회전과 부호의 대응, 회전당 카운트는 실기로 확정해야 한다.

## 12. 조사 내용과 측정값

현재 작업 트리의 소스·HAL 드라이버·CubeMX 파일·프로토콜·기존 추가 문서를 대조했다. 두 입력의 모드와 방향 판정 규칙이 같고, 경계 처리·상태 전송·설정 관리 위치가 다름을 확인했다.

실제 전압·전류·파형·회전당 카운트 측정은 수행하지 않았다. 이 문서의 카운트 예와 PWM 주파수 계산은 실기 측정 결과가 아니다.

## 13. 원인

차이는 센서 신호를 세는 원리가 바뀌어서가 아니라 모터1의 기존 상태값 경로를 유지하면서 모터2에 별도 진단 카운터와 패킷 필드를 추가했기 때문이다. 센서 모델, 두 엔코더의 실제 분해능·감속비·전기적 특성이 같은지는 미확정이다.

## 14. 해결 또는 임시 조치

현재 구현 비교를 독립 문서로 정리했다. 펌웨어·프로토콜·배선은 수정하지 않았다. 동일성을 판단할 때는 “x1 판독 규칙은 같음”과 “전송값·오버플로 처리·CubeMX 관리 방식은 다름”을 구분한다.

## 15. 검증 결과

- 현재 C 소스와 `.ioc`의 핀, IRQ, 변수, 콜백, 전송 경로를 대조했다.
- 문서의 상대 파일 링크와 코드 위치를 확인했다.
- 문서만 추가하여 이번 작업에서는 STM32·ESP32 재컴파일, 플래시, 실기 시험을 수행하지 않았다.
- 선행 문서에는 STM32·ESP32 컴파일 성공 기록이 있다. 이는 이전 작업 결과이며 실기 검증 완료를 의미하지 않는다.

## 16. 남은 위험과 후속 작업

1. 모터 전원 차단·기구 안전 확보 후 로직 전원 상태에서 축을 움직여 모터1 `encoderCount`, 모터2 `motor2_encoder_count`의 독립 증감과 정회전 부호를 확인한다.
2. 두 센서의 전압, 출력 방식, 외부 풀업, 회전당 A 펄스 수, 엔코더 장착 축과 감속비를 확인한다. 같은 x1 방식이어도 센서 분해능이 다르면 한 바퀴의 카운트는 다르다.
3. 실제 출력축 한 바퀴의 카운트 `counts_per_output_rev`가 확정되면 각도는 `count × 360 / counts_per_output_rev`, RPM은 `Δcount × 60000 / (counts_per_output_rev × Δt_ms)`로 환산할 수 있다. 이는 향후 구현식이며 현재 적용된 코드가 아니다.
4. 두 입력 모두 EXTI 처리 지연·노이즈·펄스 누락 가능성이 있으므로 속도를 높이기 전에 파형과 실측 회전수를 비교한다. 무펄스 상태만으로 정지와 센서 단선을 구분할 수 없다.
5. 장시간 누적을 사용할 경우 모터1의 int32 경계 처리도 검토한다. 모터2의 명시적 순환 역시 무한 누적을 뜻하지 않으므로 향후 차분 계산은 순환 경계를 고려해야 한다.
6. 자동 모드 전환에 쓰기 전 엔코더 기반 정지 판정, 센서 이상 검출, 제한 시간과 로컬 인터록을 별도 구현·검증한다. 특히 모터1 정지 전 정렬 금지, 모터2 정지 전 클러치 구동 금지, 모터3 동작 중 모터1·2 정지 조건을 지켜야 한다.
