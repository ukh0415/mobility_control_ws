# STM32CubeIDE 한글 경로 GDB 심볼 로딩 실패

## 발생 시각과 환경

- 발생·조치 시각: 2026-09-04 14:50 KST
- 운영체제: Windows
- IDE: STM32CubeIDE
- 디버거: ST-LINK GDB server / `arm-none-eabi-gdb`
- 유효한 STM32 프로젝트: `stm32/mobility/`
- 원래 프로젝트 절대 경로에 `대학`, `공모전`, `스마트 모빌리티 대학생 창업캠프`, `제어` 등 한글 폴더명이 포함됨

## 사용한 코드 버전 또는 Git 커밋

- 확인 당시 Git 커밋: `01b740a`
- 확인 당시 브랜치: `main`
- 작업 트리에 기존 미커밋 변경이 있었으며, 본 조치에서는 STM32 소스 코드와 공용 프로토콜을 변경하지 않음

## 증상

STM32CubeIDE에서 `mobility Debug`를 시작하면 final launch sequence에서 다음 오류가 발생했다.

```text
Failed to execute MI command:
symbol-file ".../stm32/mobility/Debug/mobility.elf"

Error message from debugger back end:
Can't read symbols from .../Debug/mobility.elf: No such file or directory
```

오류 창의 경로에서 한글 폴더명이 깨진 문자열로 표시됐다. IDE가 `mobility.elf`를 찾지 못해 심볼을 읽지 못했고 디버그 실행이 중단됐다.

## 재현 절차

1. 한글 폴더가 포함된 원래 절대 경로에서 `stm32/mobility/` 프로젝트를 STM32CubeIDE로 연다.
2. Debug 구성을 빌드한다.
3. `mobility Debug`를 실행한다.
4. GDB의 `symbol-file` 명령에서 한글 절대 경로가 깨지고 `No such file or directory`가 발생하는지 확인한다.

## 기대 동작

STM32CubeIDE가 다음 ELF 파일을 정상적으로 읽고 ST-LINK 디버그 세션을 시작해야 한다.

```text
stm32/mobility/Debug/mobility.elf
```

## 조사 내용과 측정값

- 실제 ELF 파일 존재 확인: 성공
- 확인한 파일: `stm32/mobility/Debug/mobility.elf`
- 파일 크기: `830816` bytes
- 파일 수정 시각: 2026-09-04 14:37:24 KST
- launch 파일의 프로그램 경로: `Debug/mobility.elf`
- launch 파일의 프로젝트명: `mobility`
- `.cproject`의 Debug 산출물 이름: `${ProjName}.elf`

따라서 빌드 산출물이 없거나 launch 파일에 ELF 상대 경로가 잘못 입력된 상황은 아니었다. IDE가 상대 경로를 원래 프로젝트의 절대 경로로 확장한 후 GDB 백엔드에 전달하는 과정에서 한글 부분이 깨진 것이 관찰됐다.

## 원인

STM32CubeIDE와 GDB/MI 백엔드 사이에서 한글이 포함된 Windows 절대 경로의 문자 인코딩이 일치하지 않아, GDB가 실제 경로와 다른 깨진 경로를 전달받은 것이 원인이다.

ST-LINK 연결, MCU 상태 또는 펌웨어 링크 실패가 직접 원인은 아니다. ELF가 실제 위치에 존재하고 launch 설정도 올바른 상대 경로를 사용한다는 점으로 이를 구분했다.

## 해결 또는 임시 조치

원래 저장소를 영문 드라이브 문자 `M:`에 연결했다.

```powershell
subst M: "C:\Users\oiste_pnihbwy\Desktop\대학\공모전\스마트 모빌리티 대학생 창업캠프\제어"
```

이 명령은 파일을 복사하거나 이동하지 않고 동일한 저장소에 짧은 경로 별칭을 만든다. 이후 STM32CubeIDE에서 다음과 같이 조치했다.

1. 기존 `mobility` 프로젝트를 workspace에서만 제거했다.
2. 삭제 창의 `Delete project contents on disk`는 선택하지 않았다.
3. `File > Import > General > Existing Projects into Workspace`를 선택했다.
4. root directory로 `M:\stm32\mobility`를 지정했다.
5. `Copy projects into workspace`는 선택하지 않았다.
6. 프로젝트 Location이 `M:\stm32\mobility`인지 확인했다.
7. 프로젝트를 Clean/Build한 뒤 Debug 구성을 다시 실행했다.

`subst` 연결은 일반적으로 Windows 재부팅 후 사라지므로, 재부팅 뒤 `M:`이 없으면 같은 명령을 다시 실행해야 한다. 또한 STM32CubeIDE와 `subst` 명령은 같은 사용자 권한 수준에서 실행해야 한다.

연결 확인과 해제 명령은 다음과 같다.

```powershell
subst
subst M: /D
```

## 남은 위험과 후속 작업

- 재부팅 후 `M:` 연결이 사라질 수 있으므로 디버깅 전 `subst`로 연결 상태를 확인한다.
- IDE를 관리자 권한으로 실행하면 일반 권한 터미널에서 만든 드라이브 연결이 보이지 않을 수 있다. 가능하면 둘을 동일한 권한으로 실행한다.
- 다른 드라이브 문자를 사용하거나 원래 프로젝트 경로로 다시 Import하면 같은 문제가 재발할 수 있다.
- 장기적으로는 저장소 자체를 영문·숫자로만 이루어진 경로에 배치하는 방법도 고려할 수 있지만, 저장소 외부의 과거 STM32 프로젝트 복사본을 유효 프로젝트로 사용해서는 안 된다.

## 2026-09-17 재발 확인과 바로 따라 하는 복구 절차

### 이번 확인 결과

- `M:` 드라이브 매핑이 없는 상태였다.
- 실제 저장소의 `stm32/mobility/.project`, `.cproject`, `mobility.ioc`는 모두 존재했다.
- 따라서 프로젝트 파일이 삭제된 문제가 아니며 새 프로젝트를 만들거나 파일을 복사할 필요가 없다.
- 자동화 도구의 명령 세션에서는 아래 `subst` 명령으로 같은 저장소를 `M:`에 연결하고
  `M:\stm32\mobility`에서 위 세 프로젝트 파일의 접근을 확인했다.
- Windows의 드라이브 별칭은 실행 권한과 세션에 따라 다른 프로그램에서 보이지 않을 수
  있으므로, CubeIDE가 실행되는 사용자 세션의 PowerShell에서 같은 명령을 직접 실행하고
  IDE의 Browse 창에서 `M:`이 보이는지 확인해야 한다.

### 재부팅 후 M:이 안 보일 때

STM32CubeIDE를 일반 권한으로 실행했다면 PowerShell도 일반 권한으로 열고 다음 명령을
그대로 실행한다. CubeIDE를 관리자 권한으로 실행한 경우에는 PowerShell도 같은 관리자
권한이어야 한다.

```powershell
subst M: "C:\Users\oiste_pnihbwy\Desktop\대학\공모전\스마트 모빌리티 대학생 창업캠프\제어"
```

다음 두 명령으로 매핑과 프로젝트 파일을 확인한다.

```powershell
subst
Test-Path "M:\stm32\mobility\.project"
```

정상이면 `subst` 목록에 `M:\`이 표시되고 `Test-Path` 결과가 `True`다.

### CubeIDE에서 다시 가져오기

1. Import 창이 이미 열려 있다면 취소하고 `M:` 매핑부터 만든다.
2. Project Explorer에 기존 `mobility`가 남아 있고 Location이 끊겼거나 C:의 한글 경로를
   가리키면 프로젝트를 workspace에서만 제거한다.
3. 삭제 확인 창에서 **`Delete project contents on disk`를 절대로 선택하지 않는다.**
4. `File > Import > General > Existing Projects into Workspace`를 연다.
5. `Select root directory`에 `M:\stm32\mobility`를 입력하거나 Browse로 선택한다.
6. 목록에 나타나는 `mobility` 프로젝트를 선택한다.
7. **`Copy projects into workspace`는 선택하지 않는다.**
8. `Finish`를 누른다.
9. 프로젝트 Properties의 Location이 `M:\stm32\mobility`인지 확인한다.
10. `Project > Clean`에서 `mobility`를 정리한 뒤 Build한다.
11. Build가 성공해 `M:\stm32\mobility\Debug\mobility.elf`가 생성되면 Debug를 실행한다.

Import 목록이 비어 있으면 먼저 다음을 확인한다.

- `Test-Path "M:\stm32\mobility\.project"`가 `True`인지 확인한다.
- CubeIDE와 PowerShell의 관리자 권한 수준이 같은지 확인한다.
- root directory를 `M:\stm32`가 아니라 `M:\stm32\mobility`로 정확히 지정한다.
- 같은 이름의 `mobility` 프로젝트가 workspace에 이미 있으면 먼저 workspace에서만 제거한다.

### M:이 다른 위치를 가리키거나 명령이 실패할 때

먼저 `subst`만 입력하여 현재 연결을 확인한다. `M:`이 잘못된 위치를 가리키는 경우에만
다음 명령으로 별칭을 해제한 뒤 위의 생성 명령을 다시 실행한다.

```powershell
subst M: /D
```

`M:`은 실제 파일 저장 위치가 아니라 현재 저장소를 가리키는 별칭이다. 별칭을 해제해도
저장소 파일은 삭제되지 않는다. 반대로 CubeIDE 삭제 창에서 디스크 내용 삭제를 선택하면
실제 저장소가 삭제될 수 있으므로 선택하면 안 된다.
