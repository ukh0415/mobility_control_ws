## 2. 기존 제어 흐름 분석

```text
키보드 입력
  → robot_control_client_serial.py가 문자 1바이트 전송
  → ESP32 Serial 수신
  → ESP32 Wire.write(cmd)
  → I2C 주소 0x10의 STM32 수신 콜백
  → ApplyCommand(cmd)
  → PWM 및 방향 GPIO 출력
```

| 명령 | 대상 | STM32 출력 | 의미 |
|---|---|---|---|
| `i` / `,` | 모터1: 휠 구동 | TIM3 CH1 PA6, PA7/PB0 | 정/역회전 |
| `j` / `l` | 모터2: 선기어 | TIM1 CH1 PA8, PB1/PB10 | 정/역회전 |
| `u` / `o` | 모터3: 클러치 | TIM2 CH3 PA2, PB8/PB9 | 정/역회전 |
| `k` | 전체 | TIM1/TIM2/TIM3 | 모든 모터 정지 |

Python 클라이언트는 현재 장치에 맞게 `COM10`에서 `COM9`로 조정했다. 이동 키를 누르는 동안 약 0.1초 간격으로 명령을 반복하고, 활성 이동 키가 없으면 `k`로 정지를 유지한다.

## 3. 2번 모터 엔코더 추가

## 증상

- 모터1은 회전하며 엔코더 값이 출력됐다.
- 모터2는 회전했지만 별도 엔코더 값을 읽거나 전송하지 않았다.
- 기존 상태 패킷은 `mode + int16` 총 3바이트라 엔코더 하나만 담을 수 있었다.

## 재현 절차

1. PC에서 `j` 또는 `l`을 입력한다.
2. 모터2가 회전하는 것을 확인한다.
3. 기존 ESP32 상태 출력에 모터1 엔코더 값 하나만 나타나는 것을 확인한다.

## 기대 동작

- 모터1과 모터2 원시 엔코더 카운트가 독립적으로 표시되어야 한다.
- `j/l`에서 `enc2`가 방향에 따라 증가 또는 감소해야 한다.

## 조사 내용과 측정값

기존 코드에는 PA4 상승 에지와 PA5 방향 입력을 사용하는 모터1 엔코더만 존재했다. 모터2용 PB3/PB5 배선 계획은 있었지만 GPIO, EXTI3, 별도 카운터와 상태 패킷 필드가 구현되지 않았다.

### STM32CubeMX 설정

| 핀 | 설정 | 용도 |
|---|---|---|
| PB3 | `MOTOR2_ENC_A`, GPIO_EXTI3, Rising edge | 엔코더 A상 |
| PB5 | `MOTOR2_ENC_B`, GPIO Input | 엔코더 B상 방향 판별 |

- EXTI line 3 interrupt 활성화, Preemption Priority `5`, Sub Priority `0`
- SYS Debug를 `Serial Wire`로 설정해 JTAG 핀 PB3을 GPIO/EXTI로 사용
- CubeMX 코드 생성 후 `EXTI3_IRQHandler()`와 GPIO 초기화 확인

### STM32 코드 변경

- `motor2EncoderCount` 32비트 누적 카운터 추가
- `motor2EncoderRaw` 16비트 전송값 추가
- PB3 상승 에지에서 PB5를 읽어 증가/감소 판별
- 상태 버퍼 및 I2C 송신 길이를 3바이트에서 5바이트로 확장

```text
byte 0      : mode
byte 1..2   : motor1 encoder count, int16 little-endian
byte 3..4   : motor2 encoder count, int16 little-endian
```

### ESP32와 프로토콜 변경

- `Wire.requestFrom(addr, 5)`로 상태 5바이트 요청
- 두 개의 `int16` 값을 little-endian으로 복원
- Serial 출력에 `enc1`, `enc2` 추가
- PC 상태 문자열을 다리별 `mode,enc1,enc2` 구조로 확장
- `protocol/protocol.md`와 `VERSION.md`의 프로토콜 버전을 `0.2.0-draft`로 갱신

현재 값은 보정된 각도가 아니라 원시 엔코더 `count`다. 실제 각도로 변환하려면 PPR/CPR, 감속비와 기구비가 필요하다.

## 원인

모터2 엔코더의 GPIO, EXTI 콜백, 별도 카운터 및 I2C 상태 패킷 필드가 구현되지 않았다.

## 해결 또는 임시 조치

PB3/PB5와 EXTI3를 설정하고 별도 카운터를 구현했으며, STM32와 ESP32 상태 패킷을 동시에 5바이트로 변경했다.

## 검증 결과

- `i`에서 모터1 회전 및 `enc1` 변화 확인
- `j`에서 모터2 회전 확인
- `enc2`가 `0, -68, -151, ...` 형태로 연속 변화하는 것을 확인
- `writeErr=0`, `bytesReceived=5`, `leg[0] addr=0x10 ok=true` 확인
- PB3/PB5 입력, EXTI3 처리, STM32→ESP32→PC 전달이 실기에서 동작함을 검증

## 6. 모터3 미해결 문제

## 증상

- `u`, `o` 모두 명령은 반복 전송되지만 모터3이 실제 회전하지 않는다.
- `enc1`, `enc2`는 모터1/2 피드백이므로 모터3 동작 여부를 나타내지 않는다.
- `currentMode`가 갱신되지 않아 `mode=0` 역시 `u/o` 적용 실패를 뜻하지 않는다.

## 조사 내용과 측정값

```text
cmd=u 또는 cmd=o
writeErr=0
bytesReceived=5
leg[0] addr=0x10 ok=true
```

- Python → ESP32 → STM32 `0x10` 통신은 정상이다.
- STM32의 모터3 코드는 엔코더 추가 전후가 동일하다.
- `u`: TIM2 CH3 PA2 PWM 60%, PB8/PB9 방향 출력
- `o`: 같은 채널에서 방향 반전, PWM 60%
- TIM2 초기화와 `HAL_TIM_PWM_Start()`가 존재한다.
- 모터3에 대한 별도 엔코더, 전압 또는 전류 측정값은 아직 없다.
- 연속 모터 시험 중 `u` 전환 시 `enc1/enc2`가 큰 값에서 0 근처로 바뀐 로그가 있어 전원 강하나 STM32 재부팅 가능성을 의심했지만, 처음부터 `u`만 실행한 시험에서는 원래 카운트가 0이어서 재부팅 여부를 확정하지 못했다.

## 원인

통신 앞단은 정상이며, 원인은 다음 하드웨어 구간으로 좁혀졌다. 아직 측정이나 교차시험으로 확정하지 않았으므로 `미확정`이다.

```text
STM32 PA2/PB8/PB9
  → 두 번째 L298N ENA/IN1/IN2
  → L298N OUT1/OUT2
  → 5V 전원 및 모터/클러치 기구
```

가능성:

- 두 번째 L298N 로직 또는 모터 전원 미공급
- STM32 5V 핀을 모터/L298N 전원원으로 잘못 사용
- ENA 점퍼와 PA2 PWM 배선 문제
- 공통 GND 누락
- L298N 채널 또는 모터 불량
- 클러치 기구 걸림이나 종단 도달
- 5V 전원의 전류 용량 부족과 전압 강하

## 해결 또는 임시 조치

- 장시간 스톨 시험을 중단하고 `u/o`는 0.5~1초 이내로만 시험했다.
- 원인을 확정하기 전 PWM을 무작정 높이거나 안전 로직을 우회하지 않았다.
- 종료 시 `k`를 전송하고 모터 전원을 차단했다.

## 남은 위험과 후속 작업

### 내일 가장 먼저 할 일

1. 전원을 모두 끄고 두 번째 L298N 배선을 사진과 표로 기록한다.
2. `PA2→ENA`, `PB8→IN1`, `PB9→IN2`, `모터3→OUT1/OUT2`를 확인한다.
3. PA2 PWM 사용 시 해당 채널의 ENA 점퍼가 제거됐는지 확인한다.
4. 모터 전원을 STM32 5V 핀에서 가져오지 않는지 확인한다.
5. 별도 5V 전원의 전류 용량과 모든 장치의 공통 GND를 확인한다.
6. 멀티미터가 있으면 `u/o`에서 PB8/PB9, ENA 및 OUT1/OUT2 전압을 측정한다.
7. 전원을 끈 상태에서 정상 모터와 의심 채널을 교차 연결해 드라이버와 모터 불량을 분리한다.
8. 무부하로 `u/o`를 각각 0.5~1초만 시험하고 즉시 `k`로 정지한다.

### 소프트웨어 후속 작업

- 마지막 적용 명령 또는 활성 모터를 상태에 포함해 `mode=0`만 보이는 진단 한계를 개선한다.
- 모터3 구동 전에 모터1·2를 정지하는 로컬 인터록을 STM32에 구현한다.
- 모터3 제한 시간과 종단 리미트 센서를 추가해 스톨을 방지한다.
- 엔코더 PPR/CPR과 감속비를 확정해 count→각도 변환을 구현한다.
- 16비트 전송값과 32000 카운트 순환 정책을 장기 위치 제어 관점에서 재검토한다.
- ESP32 Core 버전 호환성을 검토한 뒤 `server.available()`를 `server.accept()`로 변경한다.

### Git 정리 주의사항

- CubeMX 생성으로 HAL/CMSIS 파일 다수가 줄바꿈 차이로 수정된 것처럼 보인다.
- `git add .`를 바로 사용하지 말고 의미 있는 변경과 자동 생성/줄바꿈 변경을 구분한다.
- 기능과 문서를 분리해 다음과 같이 커밋하는 방식을 권장한다.

```text

```

- 개인 COM 포트와 IDE workspace 설정을 팀 저장소에 포함할지 검토한다.
- 5바이트 프로토콜은 STM32와 ESP32를 항상 함께 배포해야 한다.

### 경험의 핵심

- 센서 채널 추가에 맞춰 GPIO/EXTI, 펌웨어 구조, I2C 패킷, 상위 로그와 프로토콜 문서를 함께 변경했다.

### STAR 구조

- **Situation:** 모터2는 회전하지만 엔코더 데이터가 보이지 않았고, 코드 생성 뒤 빌드·디버그·업로드 오류가 연속 발생했다.
- **Task:** 기존 구조를 유지하며 모터2 엔코더를 추가하고 PC 로그까지 신뢰성 있게 전달해야 했다.
- **Action:** PB3/PB5와 EXTI3를 설정하고 별도 카운터를 구현했다. I2C 상태 패킷을 3바이트에서 5바이트로 확장하고 ESP32 파서와 프로토콜 문서를 함께 수정했다. TEMP 절대 경로, 한글 경로, ESP32 부트 모드 문제를 로그 기반으로 분리 해결했다.
- **Result:** STM32 빌드 0 errors/0 warnings와 양쪽 보드 업로드를 완료했고, 실제 `j` 구동에서 `enc2`의 연속 변화를 확인했다. 모터3 문제도 통신이 아닌 전원·드라이버 구간으로 조사 범위를 축소했다.

### 자기소개서 문장 초안

> ESP32와 STM32 기반 로봇 제어 프로젝트에서 모터2 엔코더 데이터가 상위 제어기로 전달되지 않는 문제를 해결했습니다. 키 입력부터 USB Serial, ESP32 I2C, STM32 인터럽트까지 신호 흐름을 단계별로 추적해 PB3/PB5 엔코더 입력과 EXTI3 처리가 누락된 것을 확인했습니다. STM32 카운터를 추가하고 상태 패킷을 3바이트에서 5바이트로 확장한 뒤 ESP32 파서와 프로토콜 문서까지 함께 갱신했습니다. 또한 이전 개발환경의 TEMP 경로와 한글 경로로 인한 빌드·디버깅 오류를 분리 해결하여 STM32 빌드 0 errors/0 warnings 및 양쪽 보드 업로드를 완료했습니다. 그 결과 실제 모터2 구동에서 엔코더 카운트가 연속적으로 수신되는 것을 검증했으며, 남은 모터3 문제도 통신이 아닌 전원·드라이버 구간으로 범위를 좁혀 후속 시험 계획을 수립했습니다.
